# 批次追溯设计

> 对应需求文档第 6 周 / 第 5 部分难点（追溯是 MES 最有辨识度的能力）。
> 本文档记录**实际实现**与**真实测试结果**。

---

## 1. 为什么制造业必须有批次追溯

### 1.1 三个真实场景

| 场景 | 没有追溯会怎样 | 有追溯怎么做 |
|---|---|---|
| **质量事故召回** | 某供应商的芯片有缺陷 → 不知道哪些成品用了它 → **只能全部召回**（损失巨大） | 正向追溯：查出所有用了该批次的成品批次 → **精准召回** |
| **客诉定位** | 客户投诉某台电表计量不准 → 不知道用了哪批料、谁做的 → 只能换新 | 反向追溯：查出用了哪些物料批次 + 供应商 + 工单 → **定位根因** |
| **合规要求** | 汽车/医疗/电子行业**强制要求**批次可追溯 → 没有就不合格 | 完整批次链路 + 追溯报告 |

### 1.2 追溯的业务价值（面试要讲）

> **这是 MES 区别于普通 CRUD 系统最有说服力的能力。**
> 普通系统也能"记录数据"，但只有追溯能回答
> "这个成品是怎么来的、上游是哪些料、谁做的、检没检过"。

## 2. 数据结构：有向无环图（DAG）

### 2.1 为什么是图不是树

```
物料批次(MB001 芯片) ──消耗 102──> 产品批次(PB001)
物料批次(MB002 表壳) ──消耗 101──> 产品批次(PB001)
物料批次(MB003 螺丝) ──消耗 420──> 产品批次(PB001)
物料批次(MB001 芯片) ──消耗  82──> 产品批次(PB002)   ← 同一原料批次用于多个工单
```

| 关系 | 说明 |
|---|---|
| 一个物料批次 → 多个产品批次 | 1:N（同一批芯片供多个工单） |
| 一个产品批次 → 多个物料批次 | N:1（一个成品消耗多种料） |
| 结论 | **多对多的有向无环图（DAG）** |

**如果建模成树**：只能表达"一个父节点对应一个子节点"，
无法表达"一个芯片批次影响了 2 个成品批次"——而**这恰恰是召回场景的核心**。

### 2.2 图的两个要素

**节点**：`product_batch` 表

```sql
CREATE TABLE product_batch (
    id                  BIGINT PRIMARY KEY,
    batch_no            VARCHAR(64) NOT NULL,   -- 批次号唯一
    batch_type          TINYINT NOT NULL,       -- 1-物料批次 2-产品批次
    material_id         BIGINT,                 -- 物料批次用
    product_id          BIGINT,                 -- 产品批次用
    production_order_id BIGINT,                 -- 产品批次关联工单
    quantity            DECIMAL(18,4),
    supplier_id         BIGINT,                 -- 🔑 物料批次的追溯源头
    quality_status      TINYINT,
    status              TINYINT,
    ...
    UNIQUE KEY uk_batch_no (batch_no)
);
```

**边**：`batch_relation` 表

```sql
CREATE TABLE batch_relation (
    id                  BIGINT PRIMARY KEY,
    source_batch_id     BIGINT NOT NULL,   -- 源批次（被消耗的物料批次）
    target_batch_id     BIGINT,            -- 目标批次（产出的产品批次）
    production_order_id BIGINT,            -- 追溯上下文：哪个工单
    quantity            DECIMAL(18,4),     -- 消耗量
    relation_type       VARCHAR(32),       -- CONSUME-领料消耗 OUTPUT-完工产出
    is_reversed         TINYINT DEFAULT 0, -- 退料冲正标记
    KEY idx_relation_source (source_batch_id),   -- 正向追溯用
    KEY idx_relation_target (target_batch_id),   -- 反向追溯用
    KEY idx_relation_order (production_order_id)
);
```

### 2.3 为什么物料批次和产品批次用一张表

| 理由 | 说明 |
|---|---|
| 结构高度相似 | 都有批次号、数量、状态、入库时间 |
| **追溯时节点类型必须统一** | BFS 遍历时拿到的节点类型一致，代码可以通用 |
| 代价 | 某些字段对某类型为 null（`supplier_id` 只对物料批次有意义） |

**这是有意的取舍**：表少、代码统一。
如果分开建两张表，追溯代码要写两套（物料侧 + 产品侧），且跨类型遍历时要不断判断。

### 2.4 为什么必须存 supplier_id

**质量事故的追溯终点往往是"哪个供应商的哪批料"。**

```
没有 supplier_id：成品 → 物料批次 → ??? 断了
有 supplier_id：  成品 → 物料批次 → 供应商 → 可以联系供应商封存同批次
```

实测输出：

```
反向追溯完成：共涉及 4 个批次（含起点）
└─ [MB-DEMO-1] MAT-1 演示物料1  数量=102.0  供应商=深圳华芯电子有限公司
└─ [MB-DEMO-2] MAT-2 演示物料2  数量=101.0  供应商=东莞精塑制品厂
└─ [MB-DEMO-3] MAT-3 演示物料3  数量=420.0  供应商=苏州标准件有限公司
```

## 3. 两个方向的遍历

### 3.1 反向追溯（成品 → 原料）

```java
public TraceResultVO backward(String batchNo, int maxDepth) {
    ProductBatch root = requireBatch(batchNo);
    int limit = maxDepth <= 0 ? CommonConstants.MAX_TREE_DEPTH : maxDepth;

    // 一次性查出全图边，按 target 分组（target → 它的上游边）
    List<BatchRelation> allEdges = relationMapper.selectAllActive();
    Map<Long, List<BatchRelation>> incoming = new HashMap<>();
    for (BatchRelation e : allEdges) {
        if (e.getTargetBatchId() != null) {
            incoming.computeIfAbsent(e.getTargetBatchId(), k -> new ArrayList<>()).add(e);
        }
    }

    // BFS 逐层展开
    Walk<BatchRelation> walk = walk(root.getId(), incoming::get,
            BatchRelation::getSourceBatchId, limit);
    List<TraceNode> tree = buildTree(walk.childrenOf.get(root.getId()), walk, 1, new HashSet<>());
    ...
}
```

**业务用途**：客户投诉 → 查出用了哪些料、哪个供应商、哪个工单 → 定位根因。

### 3.2 正向追溯（原料 → 成品）

```java
Map<Long, List<BatchRelation>> outgoing = new HashMap<>();
for (BatchRelation e : allEdges) {
    if (e.getSourceBatchId() != null && e.getTargetBatchId() != null) {
        outgoing.computeIfAbsent(e.getSourceBatchId(), k -> new ArrayList<>()).add(e);
    }
}
Walk<BatchRelation> walk = walk(root.getId(), outgoing::get,
        BatchRelation::getTargetBatchId, limit);
```

**业务用途**：某供应商芯片批次有缺陷 → 查出所有受影响成品 → **精准召回**。

实测：

```
正向追溯完成：该批次影响 1 个下游批次
└─ [PB-DEMO-1] PRD-DB-X1 智能电表 X1  数量=102.0
```

### 3.3 两个方向的对照

| | 反向追溯 | 正向追溯 |
|---|---|---|
| 输入 | 产品批次号 | 物料批次号 |
| 遍历方向 | 沿 `source_batch_id` 向上 | 沿 `target_batch_id` 向下 |
| 分组键 | `target_batch_id` | `source_batch_id` |
| 输出 | 全部上游物料批次 + 供应商 | 全部下游产品批次 |
| 业务场景 | 客诉定位根因 | 质量事故精准召回 |

## 4. 三个必须处理的工程问题

### 4.1 防环（最重要）

**为什么要有**：业务上不该有环，但**数据可能配错**：

- 人工录入错误把 A 的产出关联到 B，又把 B 的产出关联到 A
- 批量导入脚本 bug
- 历史数据迁移遗留

**不防环的后果**：BFS 无限循环 → **StackOverflow / 服务被打挂**。

**双重防护**：

**第一层：BFS 的 `visited` 集合**

```java
private <E> Walk<E> walk(Long startId, Function<Long, List<E>> edgeLookup,
                         Function<E, Long> nextSelector, int maxDepth) {
    Walk<E> walk = new Walk<>();
    walk.visited.add(startId);
    ...
    for (Long nodeId : currentLevel.keySet()) {
        List<E> edges = edgeLookup.apply(nodeId);
        for (E edge : edges) {
            Long next = nextSelector.apply(edge);
            if (!walk.visited.contains(next)) {
                nextLevel.computeIfAbsent(next, k -> new ArrayList<>());
            }
        }
    }
    walk.visited.addAll(nextLevel.keySet());
    ...
}
```

**第二层：buildTree 的 `emitted` 集合**

```java
private <E> List<TraceNode> buildTree(List<ChildRef<E>> children, Walk<E> walk,
                                      int level, Set<Long> emitted) {
    for (ChildRef<E> ref : children) {
        Long childId = ref.childId;
        if (!walk.visited.contains(childId)) continue;

        // 🔑 环路防护：已经在结果树中出现过的批次不再重复展开
        if (!emitted.add(childId)) {
            log.warn("[追溯] 检测到重复节点/环路，已剪枝 batchId={}", childId);
            continue;
        }
        ...
        List<TraceNode> sub = buildTree(walk.childrenOf.get(childId), walk, level + 1, emitted);
    }
}
```

**为什么需要两层**：
`childrenOf` 里的父子关系可能在数据有环时形成 A→B→A 的循环引用。
`visited` 只控制"是否展开"，但 `childrenOf` 本身仍含环 → buildTree 递归会无限深入。
**`emitted` 是防止 buildTree 无限递归的最后防线。**

> 这个缺陷是**单元测试发现的**：`testCycleDetection` 一开始抛 StackOverflow。

### 4.2 深度限制

**为什么**：

- 异常数据可能导致链路极长（如一条产线几百层），查询爆炸、响应超大
- 前端树形展示超过 10 层用户也无法阅读

**实现**：

```java
int limit = maxDepth <= 0 ? CommonConstants.MAX_TREE_DEPTH : maxDepth;   // 默认 10

// 到达深度上限时：本层节点仍然显示（只是不再向下展开）
if (depth == maxDepth) {
    walk.visited.addAll(nextLevel.keySet());
    walk.maxDepth = depth;
    // 若本层节点自身还有出边，说明结果确实不完整 → 标记截断
    for (Long nodeId : nextLevel.keySet()) {
        List<E> deeper = edgeLookup.apply(nodeId);
        if (deeper != null && !deeper.isEmpty()) {
            walk.truncated = true;
            break;
        }
    }
    break;
}
```

**关键细节**：截断时必须把本层节点加入 `visited`，
否则 `buildTree` 会把它们当作"不可见节点"跳过 → **返回空树**。

> 这个缺陷也是**单元测试发现的**：`testMaxDepthTruncation` 一开始返回空树。

**返回结果含 `truncated` 标记 + 提示语**：

```json
{
  "truncated": true,
  "message": "反向追溯完成：共涉及 1 个批次（含起点）；已达深度上限 1，结果可能不完整"
}
```

**为什么要有提示语**：用户看到"只有 1 层"时需要知道是"真的只有 1 层"还是"被截断了"。
**不提示就是用错误的数据误导用户。**

### 4.3 避免 N+1 查询

**问题写法**（每层发一次 SQL）：

```java
// ❌ 递归查询：深度 5 层 × 每层 10 个节点 = 51 次查询
for (BatchRelation rel : relationMapper.selectByTarget(batchId)) {
    ProductBatch parent = batchMapper.selectById(rel.getSourceBatchId());
    trace(parent.getId());   // 递归，又发查询
}
```

**本项目写法**（一次性查出所有边，内存遍历）：

```java
// ✅ 2 次查询：一次查全部边，一次查节点详情（buildTree 中按需查）
List<BatchRelation> allEdges = relationMapper.selectAllActive();
Map<Long, List<BatchRelation>> incoming = groupByTarget(allEdges);
// 内存 BFS
```

**为什么可行**：本项目数据量小（单工厂、单车间），一次查全表完全可接受。
数据量大时应改为"按层批量查"（`WHERE target_batch_id IN (...)`）。

## 5. 批次关系如何产生

### 5.1 两个阶段

| 阶段 | 动作 | 关系状态 |
|---|---|---|
| **领料时** | 记录"消耗了哪个物料批次" | `target_batch_id = null`（产品批次还没生成） |
| **完工时** | 生成产品批次，回填 target | `target_batch_id = 产品批次 id` |

**为什么需要"待关联"中间态**：

领料发生在生产**之前**，产品批次要等**完工后**才生成。
所以 relation 的 target 暂时为空，完工后按 `productionOrderId` 回填。

```java
public int bindOrderConsumptionsToProductBatch(Long productionOrderId, String productBatchNo) {
    ProductBatch target = batchMapper.selectByBatchNo(productBatchNo);
    List<BatchRelation> pending = new ArrayList<>();
    for (BatchRelation r : relationMapper.selectByOrderId(productionOrderId)) {
        if (r.getTargetBatchId() == null) {
            pending.add(r);
        }
    }
    for (BatchRelation r : pending) {
        r.setTargetBatchId(target.getId());
        r.setTargetBatchNo(target.getBatchNo());
        relationMapper.updateById(r);
    }
    return pending.size();
}
```

### 5.2 为什么必须和领料在同一事务

```
❌ 领料成功 → 写流水 → 写批次关系（失败）
   → 库存已经扣了，但追溯链断了 → 这个批次永远查不到去向

✅ 领料 + 流水 + 批次关系 → 同一事务，全成功或全失败
```

**追溯链一旦断裂就是永久性的数据缺陷** —— 事后无法补（不知道当时领了哪批料）。

### 5.3 退料如何冲正

账本只增不改，所以退料：
1. 记一条方向相反的库存流水
2. `batch_relation` 标记 `is_reversed = 1`（或记一条新的反向边）

**为什么不物理删除关系**：追溯要能看到"曾经消耗过，后来说退了"。
直接删掉会让历史变得不可解释。

## 7. 接口设计

### 7.1 追溯查询

```
GET /trace/backward?batchNo=PB20250115001&maxDepth=0
GET /trace/forward?batchNo=MB20250101001&maxDepth=0
```

**参数**：
- `batchNo`：起点批次号（不用 id，业务可读）
- `maxDepth`：最大深度，0 表示默认 10 层

**返回结构（树形，前端可直接展开）**：

```json
{
  "direction": "BACKWARD",
  "root": { "batchNo": "PB001", "batchType": 2, "batchTypeDesc": "产品批次", ... },
  "tree": [
    {
      "level": 1,
      "batchNo": "MB001",
      "batchType": 1,
      "batchTypeDesc": "物料批次",
      "code": "MAT-MCU-01",
      "name": "计量芯片 MCU-A",
      "batchQuantity": 1000,
      "edgeQuantity": 102,
      "supplierId": 1001,
      "supplierName": "深圳华芯电子有限公司",
      "hasChildren": false,
      "children": []
    }
  ],
  "totalNodes": 4,
  "maxDepth": 1,
  "truncated": false,
  "message": "反向追溯完成：共涉及 4 个批次（含起点）"
}
```

**为什么用树形而不是平铺列表**：
- 前端可展开/折叠
- 能表达"这条原料是通过哪条路径影响的"
- 平铺列表丢失了层级关系

```
POST /batch/relation

```

## 8. 性能考虑

| 优化点 | 本项目做法 | 数据量大时应 |
|---|---|---|
| 查询次数 | 一次查全部边 + 内存 BFS | 按层批量查（`WHERE id IN (...)`） |
| 深度 | 限制 10 层 | 保持限制 |
| 结果缓存 | 未做 | Redis 缓存 5 分钟（追溯结果变化不频繁） |
| 分页 | 未做 | 节点过多时分页返回关键路径 |
| 索引 | `idx_relation_source` / `idx_relation_target` | 同 |

**为什么没做缓存**：本项目数据量小，单次追溯 < 100ms，加缓存收益不大却引入一致性问题。
**不做过早优化是合理的工程判断。**

## 9. 与其他模块的协作

```
① 物料入库（inventory-service）
   → 同时创建物料批次（quality-service），带供应商
   → 批次号写入库存流水 batch_no（追溯起点）

② 工单领料（inventory-service）
   → 领料明细记 batch_no
   → 调用 quality-service 记录"物料批次 → (待关联)"关系

③ 工单完工（production-service）
   → 生成产品批次（quality-service）
   → 回填批次关系（物料批次 → 产品批次）

④ 追溯查询（quality-service）
   → 反向：成品 → 物料 + 供应商
   → 正向：物料 → 受影响成品
```

**跨服务的数据一致性**：
领料在 inventory-service，批次关系在 quality-service —— 这是**跨服务操作**，
理论上做不到原子性。本项目的处理：
- 批次关系记录失败时**不影响领料**（业务优先），记 WARN 日志
- 由定时任务/人工补偿
- **这是一个明确的已知限制**（见 §10）

---

## 10. 已知限制

1. **批次关系与领料不在同一事务**（跨服务）：极端情况下可能"领料成功但批次关系漏记"。
   彻底解决需要把批次表并入 inventory 库，或用 outbox 保证最终一致。
2. **未做批次级库存**：不追踪"某批次还剩多少"，批次只用于追溯关系。
3. **无追溯结果缓存**：数据量大时性能需优化。
4. **未做追溯报告导出**：只有 JSON 接口，无 PDF/Excel 导出。
5. **未做客户/发货追溯**：`batch_relation` 未建模"发给哪个客户"，因此正向追溯止于成品批次。
6. **未做图数据库**：关系表 + BFS 在百万级边以内可用，更大规模需专业图存储。
