# 库存并发控制方案

> 对应需求文档第 4 周 / 第 5 部分难点 1、4。
> 本文档记录**实际实现**与**真实并发测试数据**（非估算）。

---

## 1. 业务场景与问题

### 1.1 超发是怎么发生的

```
库存: quantity=100, reserved_quantity=0（可用量 100）
工单 A 要预留 60，工单 B 要预留 50

无并发控制时：
  t1  A 读 quantity=100, reserved=0  → 可用 100 ≥ 60 ✅
  t2  B 读 quantity=100, reserved=0  → 可用 100 ≥ 50 ✅
  t3  A 写 reserved = 0 + 60 = 60
  t4  B 写 reserved = 0 + 50 = 50   ← 覆盖了 A 的写入

结果：reserved = 50，但两个工单都以为自己锁到了料
      → 领料时物料不够 → 生产停线
```

### 1.2 问题的本质

**读-判断-写三步不是原子的**：`SELECT` 到 `UPDATE` 之间，其他事务可能已修改数据。

而且这是**分布式环境**：多实例部署时 JVM 锁完全无效。

## 2. 方案对比与选型

| 方案 | 做法 | 问题 | 适用场景 |
|---|---|---|---|
| A. 悲观锁 | `SELECT ... FOR UPDATE` | 锁持有时间长（业务处理全程持有）；高并发下大量等待；死锁风险 | 强冲突、短事务 |
| B. 乐观锁 | `version` 字段 + 失败重试 | 库存是**热点行**，冲突率高 → 大量重试放大数据库压力 | 冲突少的场景 |
| **C. 条件更新（CAS）** | **把判断写进 WHERE** | 无 | ✅ **库存扣减** |
| D. Redis 分布式锁 | 加锁→查→判断→更新→解锁 | 见 §2.2 | 不合适 |

### 2.1 为什么选 C（条件更新）

```sql
UPDATE material_inventory
SET reserved_quantity = reserved_quantity + #{qty}, update_time = NOW()
WHERE material_id   = #{materialId}
  AND warehouse_id  = #{warehouseId}
  AND quantity - reserved_quantity >= #{qty}    -- 🔑 业务判断在 WHERE 里
```

四个优势：

1. **无窗口期**：判断与更新在**同一条 SQL**，中间没有任何可插入的时刻
2. **无需额外组件**：数据库行锁天然保证互斥
3. **无需重试循环**：影响行数直接给出成功/失败信号
4. **语义清晰**：库存业务是"要么够要么不够"，不像转账需要"重试到成功"

### 2.2 为什么不用 Redis 分布式锁（面试必答）

| 维度 | Redis 分布式锁 | 数据库条件更新 |
|---|---|---|
| **原子性** | 加锁 → 查库存 → 判断 → 更新 → 解锁。**锁内查到的库存可能已过期**（其他线程可能在你查完之后、加锁之前已改了数据，或者锁已超时释放） | 判断与更新同一条 SQL，**无窗口期** |
| **正确性依赖** | 锁的超时设置、看门狗续期、持有者校验 | 数据库行锁语义 |
| **故障点** | ① 锁超时提前释放 ② 主从切换丢锁 ③ 误删他人锁 ④ Redis 本身不可用 | 无额外组件 |
| **性能** | 多一次网络往返 + 锁竞争 | 单条 SQL |
| **可观测** | 需额外埋点 | 影响行数天然可观测 |

**关键论点**：

> Redis 锁不是"不能用"，而是**这个场景用了反而更差**。
> 它引入了 4 个新的故障模式，却解决不了"锁内数据过期"这个根本问题
> —— 因为锁只能保证互斥，不能保证"锁内读到的数据仍然有效"。
> 而条件更新把"判断依据"和"更新动作"合并成原子操作，从根上消除了这个问题。

### 2.3 Redisson 在本项目的正确用途

Redis 锁**应该**用在这里（而不是库存）：

| 场景 | 该不该用 Redis 锁 | 说明 |
|---|---|---|
| 库存扣减 | ❌ | 条件更新更好 |
| 工单号生成 | ⚠️ 可用但非必需 | 数据库序列/Redis INCR 更简单 |
| **定时任务防多实例重复执行** | ✅ **应该用** | 多个实例的 `@Scheduled` 会同时跑，必须选主 |
| 防止同一工单并发下达 | ⚠️ | CAS 也能做，看场景 |

> **知道什么时候不该用某个技术，比会用更重要。**

## 3. 三量模型

### 3.1 三个量

```
quantity           现有量   —— 仓库里实际有多少
reserved_quantity  预留量   —— 被工单锁定但还没领走
可用量 = quantity - reserved_quantity   ← 计算值，【不存字段】
```

**为什么可用量不存字段**：

如果存三个字段，就可能出现"quantity - reserved ≠ available"的不一致
（比如某处代码只更新了 quantity 忘了 available）。
这类不一致在生产环境极难排查，而**计算值永远不会自相矛盾**。

### 3.2 五个动作

| 动作 | quantity | reserved_quantity | 业务含义 |
|---|---|---|---|
| 入库 | **+N** | 不变 | 采购到货 |
| 预留 | 不变 | **+N** | 工单锁料，物料还在仓库 |
| 领料 | **−N** | **−N** | 物料离开仓库 |
| 释放预留 | 不变 | **−N** | 工单取消，解除锁定 |
| 退料 | **+N** | 不变 | 物料退回仓库 |

**关键理解**：
- **预留 ≠ 出库**：预留只锁定，不移动实物
- **领料才是真正的减少**：同时减 quantity 和 reserved

### 3.3 为什么分两段（预留 + 实扣）

| 方案 | 问题 |
|---|---|
| **创建工单就扣库存** | 工单取消要退回；长期不生产的工单把库存占死 |
| **领料时才扣库存** | 两个工单同时认为库存够用 → 超发 |
| **预留 + 实扣两段式** ✅ | 先锁定再消耗，既防超发又不提前扣账 |

## 4. 核心实现

### 4.1 预留（`reserveStock`）

```java
@Update("UPDATE material_inventory "
      + "SET reserved_quantity = reserved_quantity + #{qty}, update_time = NOW() "
      + "WHERE material_id = #{materialId} AND warehouse_id = #{warehouseId} "
      + "AND quantity - reserved_quantity >= #{qty}")
int reserveStock(@Param("materialId") Long materialId,
                 @Param("warehouseId") Long warehouseId,
                 @Param("qty") BigDecimal qty);
```

服务层判定：

```java
int affected = inventoryMapper.reserveStock(...);
if (affected != 1) {
    throw new BusinessException(ErrorCode.STOCK_NOT_ENOUGH,
        String.format("物料[%s %s]可用库存不足：需求量 %s %s，可用量 %s %s", ...));
}
```

### 4.2 领料（`issueStock`）

```java
@Update("UPDATE material_inventory "
      + "SET quantity = quantity - #{qty}, "
      + "    reserved_quantity = reserved_quantity - #{qty}, update_time = NOW() "
      + "WHERE material_id = #{materialId} AND warehouse_id = #{warehouseId} "
      + "AND quantity >= #{qty} "
      + "AND reserved_quantity >= #{qty}")   -- 🔑 防止领了没预留的物料
int issueStock(...);
```

**为什么必须校验 `reserved_quantity >= qty`**：
否则可以绕过预留直接领货 → 库存管控失效。

### 4.3 防死锁：按 materialId 升序

```java
// 合并同物料 + 按 materialId 升序排序
List<RequirementItem> sorted = merged.values().stream()
        .sorted(Comparator.comparing(RequirementItem::getMaterialId))
        .toList();

for (RequirementItem item : sorted) {
    int affected = inventoryMapper.reserveStock(item.getMaterialId(), warehouseId, item.getRequiredQuantity());
    if (affected != 1) throw new BusinessException(...);   // 事务回滚，前面的预留自动释放
    ...
}
```

**为什么排序能防死锁**：

```
❌ 不排序：
   事务 A: 锁物料 1 → 等物料 2
   事务 B: 锁物料 2 → 等物料 1      → 循环等待 = 死锁

✅ 升序排序：
   事务 A: 锁物料 1 → 锁物料 2
   事务 B: 锁物料 1（等 A 释放）→ 锁物料 2
   → 加锁顺序一致，不会循环等待
```

### 4.4 整体回滚

一个工单预留 3 个物料，第 2 个失败 → 第 1 个必须释放。

**实现**：整个预留方法在一个 `@Transactional` 内。
条件更新失败抛异常 → Spring 回滚 → 第 1 个物料的 `reserved` 增加也被回滚。

**实测验证**：

```
预留 物料1(需102) + 物料2(需101) + 物料4(需103, 只有5)
→ 返回 40903 物料[MAT-LCD-01]可用库存不足

关键验证：物料1和2的预留量应仍为 0（已回滚）
+-------------+-----------+-------------------+
| material_id | quantity  | reserved_quantity |
+-------------+-----------+-------------------+
|           1 | 1000.0000 |            0.0000 |   ← 已回滚 ✅
|           2 | 1000.0000 |            0.0000 |   ← 已回滚 ✅
|           4 |    5.0000 |            0.0000 |
+-------------+-----------+-------------------+

预留记录数: 0 ✅（没有部分预留的脏数据）
```

## 5. 并发测试（真实数据）

### 5.1 测试程序

`perf-test/PerfInventoryConcurrency.java`

```bash
# 参数：并发线程数 物料ID 每次预留数量 [预期成功次数]
#   - 不传第 4 参数：默认预期成功 = 线程数（"库存刚好等于总需求"场景）
#   - 传第 4 参数：用于"库存不足"场景，断言恰好这么多次成功

# 场景 A：库存 100，100 线程各预留 1
java perf-test/PerfInventoryConcurrency.java 100 1 1 100

# 场景 B：库存 50，100 线程各预留 1
java perf-test/PerfInventoryConcurrency.java 100 1 1 50
```

**为什么用不同 orderId**：`reserve` 接口按 orderId 幂等（同一工单重复预留直接返回），
所以并发测试必须用不同 orderId 才能真正打到同一行库存上。

**为什么用 CountDownLatch**：需要让所有线程**同时**发起请求，才能最大化并发冲突。
直接起线程池会让线程陆续启动，第一个可能已经完成，测不出竞态。

**三条断言**（两个场景都跑）：
1. 成功次数 == 预期成功次数（**精确相等**，不是"大约"）
2. 失败次数 == 线程数 − 预期成功次数（一个不多一个不少）
3. **可用量不为负**（`quantity >= reserved_quantity`，直接解析接口返回校验）

### 5.2 场景一：足量预留（100 线程 / 库存 100 / 每次 1）

```
==============================================
  库存并发预留测试
  物料 ID  : 1
  并发线程 : 100
  每次预留 : 1
  预期成功 : 100
==============================================

----------------------------------------------
  测试耗时 : 1.29 秒
  成功次数 : 100
  失败次数 : 0
----------------------------------------------
  最终库存 : {"quantity":100.0000,"reservedQuantity":100.0000,"availableQuantity":0.0000}

=== 断言检查 ===
  [PASS] 成功次数 == 100（实际 100）
  [PASS] 失败次数 == 0（实际 0）
  [PASS] 可用量不为负（quantity >= reserved_quantity）

*** 并发测试通过：零超卖 ***
```

**结论**：100 个并发请求，恰好 100 次成功，`quantity - reserved = 0`，**无超发**。

### 5.3 场景二：超量预留（100 线程 / 库存 50 / 每次 1）

```
==============================================
  库存并发预留测试
  物料 ID  : 1
  并发线程 : 100
  每次预留 : 1
  预期成功 : 50（库存不足，其余应被拒绝）
==============================================

----------------------------------------------
  测试耗时 : 0.77 秒
  成功次数 : 50
  失败次数 : 50
----------------------------------------------
  失败原因分布：
    [1 次] 物料[MAT-CONC]可用库存不足：需求量 1 个，可用量 49.0000 个
    [1 次] 物料[MAT-CONC]可用库存不足：需求量 1 个，可用量 41.0000 个
    ...（其余均为"可用库存不足"）

=== 断言检查 ===
  [PASS] 成功次数 == 50（实际 50）
  [PASS] 失败次数 == 50（实际 50）
  [PASS] 可用量不为负（quantity >= reserved_quantity）

*** 并发测试通过：零超卖 ***
```

数据库最终状态：

```
+-------------+-----------+-------------------+-----------+
| material_id | quantity  | reserved_quantity | available |
+-------------+-----------+-------------------+-----------+
|           1 |   50.0000 |           50.0000 |    0.0000 |
+-------------+-----------+-------------------+-----------+

预留记录数: 50
```

**结论**：恰好 50 次成功、50 次失败，`available = 0`，**无负数、无超发**，
生成的预留记录数 = 成功次数（账实一致）。

> 💡 **失败原因里"可用量 49/41/…"看起来像是"明明有货却失败"** ——
> 这是并发瞬间的真实快照：每个线程读到的是**它那一刻**的可用量，
> 而它前面已经有若干线程抢先预留成功了。所以并发下"读到 49 但还是失败"是完全正常的
> —— 因为另外 49 个线程在同一时刻也在抢。**最终结果（50 成功）才是唯一的判断标准。**

### 5.4 场景三：事务回滚（部分成功）

见 §4.4，结果：物料 1/2 的 `reserved` 仍为 **0**，预留记录 **0** 条。

### 5.5 场景四：对账

```
POST /inventory/reconcile
→ {"code":0,"message":"对账通过，未发现异常","data":0}
```

对账逻辑：
1. **现有量对账**：`inventory.quantity` vs `SUM(流水.quantity)`
2. **预留量对账**：`inventory.reserved_quantity` vs `SUM(预留表.reserved - issued)`
3. **负值检测**：任何量为负都是严重异常
4. **预留量 ≤ 现有量**

> ⚠️ **开发中发现的一个真实设计缺口**：
> 初始化库存时如果只写 `material_inventory` 而不写流水，
> 对账会立刻报 `QUANTITY_DIFF`（库存 1000 vs 流水 0）—— 这**不是 bug，而是对账在正确工作**。
> 修复方式：初始化库存必须同时生成"期初入库"流水（`transaction_type=1`）。
> 这条记录现在写在 `sql/06_init_data.sql` 里。

## 6. 预留泄漏与兜底

### 6.1 预留泄漏是什么

工单取消或长期不生产，但预留没释放 → 库存被永久锁死 → 其他工单明明有货却预占不到。

### 6.2 三重兜底

| 机制 | 实现 |
|---|---|
| ① 工单取消主动释放 | `handleSideEffects` 的 `CANCELLED` 分支 → `releaseByOrder` |
| ② 预留过期时间 | `material_reservation.expire_time`（默认 7 天） |
| ③ 定时任务清理 | 每天 02:00 扫 `status IN (1,2) AND expire_time < NOW()` 释放 |

```java
@Scheduled(cron = "0 0 2 * * ?", zone = "Asia/Shanghai")
public void releaseExpiredReservations() {
    List<MaterialReservation> expired = reservationMapper.selectExpired(LocalDateTime.now(), 500);
    for (MaterialReservation r : expired) {
        inventoryService.releaseByOrder(r.getOrderId());
    }
}
```

**幂等**：释放时用条件更新 `WHERE reserved_quantity >= qty`，重复执行不会把 `reserved` 减成负数。

### 6.3 分布式锁的适用场景

多实例部署时 `@Scheduled` 会重复执行 → 必须选主。
本项目的做法：默认单机部署，代码中标注了应改为 Redisson `tryLock(0, TimeUnit.SECONDS)`
（不传 leaseTime 启用看门狗续期）。

## 7. 账本式流水设计

### 7.1 为什么记 before/after 而不只记变动量

| 用途 | 说明 |
|---|---|
| **对账** | 末条流水的 `after_quantity` 应等于库存表当前 `quantity`，不等就是异常 |
| **排查并发 bug** | 如果两条流水的 `before` 相同，说明有并发覆盖问题 |
| **审计** | 任何时刻的库存状态都可以从流水重建 |
| **回溯** | 出问题能精确定位是哪一笔导致的 |

### 7.2 为什么只增不改不删

账本一旦可改，审计价值就没了。
发现错误要用**反向冲正**（再记一条相反方向的流水），而不是修改历史。

代码层面也强制了这一点：`InventoryTransactionMapper` **只有 insert 和 select**，
根本没有 update/delete 方法 —— 从接口层面断了"改历史"的可能。

### 7.3 流水字段

| 字段 | 用途 |
|---|---|
| `transaction_type` | 1-入库 2-出库 3-预留 4-释放预留 5-退料 6-盘点调整 |
| `quantity` | 变动量（带正负号） |
| `before_quantity` / `after_quantity` | 现有量前后值 |
| `before_reserved` / `after_reserved` | 预留量前后值 |
| `batch_no` | **批次追溯链路的起点** |
| `biz_type` / `biz_no` | 业务类型与单号（关联领料单/工单） |

## 8. 幂等设计

| 场景 | 幂等机制 |
|---|---|
| 预留 | `uk_order_material(order_id, material_id)` 唯一索引 + 先查后插 |
| 领料 | `material_issue.uk_issue_no` 唯一索引；先查 `issueNo` 是否已存在，存在直接返回 |
| 库存流水 | `transaction_no` 唯一索引 |
| 定时任务释放预留 | 条件更新 `WHERE reserved_quantity >= qty` |


## 9. 与其他模块的协作

### 9.1 物料需求从哪来

库存服务**不负责**计算 BOM 需求 —— 那是 production-service 的职责（它拥有 BOM 数据与工单）。

```
production-service: 按工单锁定的 bomId 计算需求（含损耗率、向上取整）
        ↓ HTTP（带 items 列表）
inventory-service: 做齐套分析 / 预留 / 领料
```

**为什么这样分**：
- BOM 是基础资料（product-service），工单是执行域（production-service）
- 库存服务只关心"多少量、够不够"，不关心"为什么需要这么多"
- **职责清晰：计算与扣减分离**

### 9.2 齐套分析（只算不扣）

```
POST /inventory/kitting/{orderId}
Body: [{materialId, requiredQuantity}, ...]
→ 返回每项的 需求/现有/预留/可用/是否充足/缺口数量
```

**关键设计**："只计算和比对，不扣库存" —— 计算与预留分离，用户可以先看缺料再决定补料。

实测：
```
齐套结果: 存在缺料
  缺料: MAT-LCD-01 需求=103 可用=50.0 缺口=53.0
```

## 10. 已知限制

1. **单仓库**：`warehouse_id` 已建模但固定为 1，未做多仓调拨与跨仓预留。
2. **无批次级库存**：库存按 `(material_id, warehouse_id)` 记账，未细化到批次级可用量。
   批次只用于追溯（领料时记录），不做"某批次剩多少"的精细管控。
3. **定时任务未加分布式锁**：单机部署无影响，多实例需接 Redisson。
4. **对账不自动修正（默认）**：`reconcile(autoFix=false)` 只记录异常，
   避免自动修正掩盖真实 bug。修正能力已实现但需显式传参。
5. **未做库存盘点单**：`transaction_type=6`（盘点调整）已预留，未实现盘点流程。
