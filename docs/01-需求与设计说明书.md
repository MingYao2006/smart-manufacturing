# 需求与设计说明书

> Smart-Manufacturing 智能制造生产执行系统（MES）· 设计说明
> 本文档对应开发计划书第 1 周的任务 1.1–1.5 的产出。

---

## 1. 业务背景

### 1.1 制造业车间的信息断层

```
计划部门用 Excel 排产  →  车间主任用纸质派工单  →  工人干完口头汇报
        ↓                        ↓                       ↓
   计划一变就乱            派工单丢/重          产量靠人记、质量靠抽检
        ↓                        ↓                       ↓
            库存账实不符 · 进度不可见 · 出了问题追溯不到批次
```

### 1.2 MES 要回答的四个问题

| # | 问题 | 系统能力 |
|---|---|---|
| 1 | **做什么** | 生产计划 → 生产工单 |
| 2 | **用什么做** | BOM 展开 → 物料需求 → 预留 → 领料 |
| 3 | **怎么做、做到哪了** | 工艺路线 → 工序任务 → 报工 |
| 4 | **做得怎么样** | 质检单 → 不良记录 → 批次追溯 |

### 1.3 MES 与 ERP 的边界

| 系统 | 管什么 | 时间粒度 |
|---|---|---|
| ERP | 计划、采购、销售、财务 | 天/周/月 |
| **MES** | **车间执行：工单、工序、报工、质量、追溯** | **分钟/小时** |

**本项目明确只做 MES 的执行层，不做 ERP 的计划与财务。**

## 2. 业务边界（明确不做什么）

| 维度 | 覆盖 | 不覆盖 |
|---|---|---|
| 制造类型 | 离散制造（组装类） | 流程制造（配方、罐批） |
| 生产模式 | MTO + 简单 MTS | ATO/ETO、APS 排程 |
| 规模 | 单工厂、单车间 | 多工厂、多组织 |
| 设备 | 不联网 | SCADA/OPC-UA/OEE |
| 排产 | 人工指定 | 自动排程算法 |
| 财务 | 不做 | 成本核算 |
| MRP | 单层展开 | 多级递归 + 提前期 + 批量规则 |

**为什么要明确边界**：面试被问"能支持流程制造吗"，
正确回答是"不能，因为流程制造需要配方版本管理和罐批追踪，业务模型完全不同"。
**清楚边界比假装全能更加分。**

## 3. 服务拆分设计

### 3.1 最终架构：5 个业务服务 + 1 个网关

```
gateway            9000  路由 / JWT 鉴权 / traceId
system-service     9001  用户 / 角色 / 登录
product-service    9002  产品 / 物料 / BOM / 工艺路线     ← 基础资料域
production-service 9003  计划 / 工单 / 工序任务 / 报工    ← 执行域
inventory-service  9004  库存 / 预留 / 领退料 / 流水     ← 库存域
quality-service    9005  质检 / 批次 / 追溯             ← 质量域
```

### 3.2 从 8 个服务调整到 5 个的三个决定性理由

#### 理由 1：process 必须合并进 production（致命问题）

**原方案**：`production-service` 管工单，`process-service` 管工序任务。

**问题**：

```
报工（工序服务）→ 更新工单进度（生产服务）
     ↑ 跨服务调用
```

这条链路是**每分钟都在跑的高频核心链路**。拆开后：
- 需要分布式事务（或最终一致）
- 网络抖动会直接影响报工
- 两个服务的数据库都要存"工单进度"相关数据，职责混乱

**为什么它们本就该在一起**：
- 工序任务是**工单的执行视图**（同一聚合根）
- 报工是**工单进度的唯一数据来源**
- 它们共享**同一个事务边界**

**正确的拆分依据是"事务边界和变更频率"，不是"名词"。** 这是本项目最想表达的设计判断。

#### 理由 2：quality 独立但可降级（严重问题）

**质检是工序流转的门禁**：`is_inspection=true` 的工序必须质检合格才能进下一道。

**如果拆成独立服务**："工序完成 → 等质检 → 决定是否放行"变成跨服务强同步调用，
网络抖动就会卡住产线。

**本项目的处理**：
- 质检有独立业务概念（检验项、不良代码、抽检规则），**值得独立建模** → 保留为独立服务
- 但**工序门禁通过状态机协同**：质检点工序报满后进入 `WAIT_INSPECTION` 状态，
  只有质检合格才流转到 `COMPLETED` → 后道才可开始
- 这样跨服务调用只发生"查质检结果"这一处，且可用状态兜底
- **代码中注明了降级方案**：若时间紧张，把质检表并入 production 库、逻辑写在 production 内，
  用本地事务保证原子性

#### 理由 3：inventory 必须独立

库存扣减是整个项目技术含量最高的部分：
- 并发控制（条件更新）
- 预留/实扣两段式
- 账实对账

**独立成服务才能在面试中讲成一个完整的技术专题。**

### 3.3 为什么不做 ai-assistant

AI 是锦上添花。和核心服务并列会让工期估算失真。
**诚实的做法：标注为"计划中"，不做。**

## 4. 四个状态机

### 4.1 生产工单（8 状态）

```
DRAFT(草稿) ──审核──> APPROVED(已审核) ──下达──> RELEASED(已下达)
   │                      │                        │
   │取消                   │取消                     │开工
   ▼                      ▼                        ▼
CANCELLED              CANCELLED            IN_PROGRESS(生产中)
                                                  │      │
                                          暂停    │      │ 完工
                                                  ▼      ▼
                                              PAUSED   COMPLETED(已完工)
                                                          │
                                                          │ 关闭
                                                          ▼
                                                       CLOSED(已关闭)
```

**关键约束**：
- 草稿不能直接下达（必须先审核）
- 未下达不能开工
- 终态（CLOSED / CANCELLED）不可再流转
- 所有变更走统一入口 + CAS 并发控制

详见 `docs/03-工单状态机设计.md`。

### 4.2 工序任务（6 状态）

```
PENDING(待开始) ──开始──> IN_PROGRESS(进行中) ──报满且需质检──> WAIT_INSPECTION(待质检)
   │                          │      │                            │        │
   │跳过                      │暂停   │报满且无需质检              │合格     │不合格
   ▼                          ▼      ▼                            ▼        ▼
SKIPPED(已跳过)          PAUSED   COMPLETED(已完成)          COMPLETED  IN_PROGRESS(返工)
```

**关键约束**：
- **工艺纪律**：前道工序未完成，后道不能开始
- **质检门禁**：前道是质检点且未放行，后道不能开始
- 质检点工序报满后进 `WAIT_INSPECTION`，不是直接完成

### 4.3 物料预留（4 状态）

```
RESERVED(已预留) ──部分领料──> PARTIAL_ISSUED(部分领用) ──继续领──> PARTIAL_ISSUED
      │                              │
      ├──一次领完────────────────────┴──> ISSUED(全部领用)
      │                              │
      └──工单取消/过期───────────────┴──> RELEASED(已释放)
```

### 4.4 版本化对象（BOM / 工艺路线，3 状态）

```
DRAFT(草稿) ──审核生效──> ACTIVE(生效) ──高版本生效时被顶替──> INACTIVE(失效)
```

**关键约束**：
- 同一产品同时**只能有一个 ACTIVE 版本**（否则工单不知道该用哪个）
- 已 ACTIVE 的版本**不允许修改明细**（改必须新建版本）
- "生效"是**不可逆**的（INACTIVE 不能再变回 ACTIVE）

## 5. 微服务技术选型

| 技术 | 版本 | 承担什么 | 为什么不用替代方案 |
|---|---|---|---|
| Java | 21 | 语言 | Boot 3.3 要求 17+，21 与既有项目一致 |
| Spring Boot | 3.3.6 | 基础框架 | — |
| Spring Cloud | 2023.0.1 | 微服务治理 | 严格匹配 Boot 3.3.x 官方版本表 |
| Spring Cloud Alibaba | 2023.0.1.0 | Nacos | 混用 2022.x 会 NoSuchMethodError |
| Nacos | 2.x/3.x | 注册 + 配置 | 一个组件替代 Eureka + Config |
| Gateway | 4.1.2 | 统一入口 | 单服务直连会让鉴权散落 |
| OpenFeign | 4.1.x | *（已引入，本机用 RestClient）* | 见下方说明 |
| MySQL | 8.0 | 持久化 | 业务强关系，必须事务 |
| MyBatis-Plus | 3.5.5 | ORM | CRUD 高效；条件更新直接写 SQL 更可控 |
| Redis | 7（可选） | 缓存/幂等 | **不用来做库存锁** |
| RabbitMQ | 3.x（可选） | 异步解耦 | 不用 Seata |
| Knife4j | 4.4.0 | 接口文档 | — |
| JWT (jjwt) | 0.12.3 | 无状态鉴权 | Session 需共享存储 |

### 5.1 关于服务间调用方式的说明

**本项目实际使用 `RestClient` + 可配置 baseUrl，而不是 OpenFeign。**

理由：

| 需求 | Feign | RestClient + baseUrl |
|---|---|---|
| Nacos 未启动时也能本地演示 | ❌ 无实例直接失败 | ✅ 直连端口 |
| 需要返回体错误码透传 | 需额外解码器 | ✅ 手动解析，控制精确 |
| 以后切服务发现 | ✅ 原生 | 改一个配置 |

**取舍**：优先保证"开箱即可运行"。Feign 依赖已引入，切换成本很低。
**这是一个明确记录在代码注释里的取舍，面试可直接讲。**

## 7. 关键业务规则（需求推演的产物）

这些规则是在"把 8 张流程图逐步骤走一遍，问每一步需要读写哪些字段"的过程中发现的。

### 7.1 基础资料

| # | 规则 | 原因 |
|---|---|---|
| R1 | 产品编码唯一，重复返回友好错误 | 业务约束的硬保证 |
| R2 | 停用产品不允许建工单 | 避免生产已淘汰产品 |
| R3 | 已被 BOM 引用的产品/物料不允许删除 | 物理删除的约束补偿 |
| R4 | 同一产品同时只有一个生效 BOM | 否则工单不知道用哪个 |
| R5 | 已生效 BOM 不允许改明细 | 历史工单的物料需求必须可追溯 |
| R6 | BOM 禁止循环引用 | 防止无限展开 |
| R7 | 工序号用 10/20/30 | 留出插入空间 |

### 7.2 生产执行

| # | 规则 | 原因 |
|---|---|---|
| R8 | 创建工单必须快照 `bomId` + `routeId` | 制造业铁律 |
| R9 | 没有生效 BOM/工艺路线时拒绝创建工单 | 宁可在创建时失败，也不要在下达时才发现 |
| R10 | 工单状态流转必须 CAS | 多入口并发修改 |
| R11 | 下达时同步生成工序任务（幂等） | 工序少、生成快、下达低频，无解耦收益 |
| R12 | 前道工序未完成，后道不能开始 | 工艺纪律 |
| R13 | 前道是质检点且未放行，后道不能开始 | 质检门禁 |
| R14 | 报工必须校验 合格+不良=报工 | 前端不可信 |
| R15 | 累计报工不能超过计划数量 | 防超报，条件更新保证 |
| R16 | 进度由报工**重算**而非累加 | 天然幂等，防重复消费 |
| R17 | 工单完工判定不能只靠 MQ | 必须有定时兜底扫描 |

### 7.3 库存

| # | 规则 | 原因 |
|---|---|---|
| R18 | 预留只动 `reserved`，不动 `quantity` | 预留 ≠ 出库 |
| R19 | 领料同时动 `quantity` 和 `reserved` | 物料离开仓库 |
| R20 | 预留用条件更新（`quantity-reserved >= qty`） | 并发安全 |
| R21 | 多物料预留按 `material_id` 升序 | 防死锁 |
| R22 | 多物料预留要么全成功要么全回滚 | 不产生部分预留脏数据 |
| R23 | 领料必须校验 `reserved >= qty` | 防绕过预留直接领货 |
| R24 | 库存变动必须有流水 | 对账与追溯的基础 |
| R25 | 流水只增不改 | 账本不能篡改 |
| R26 | 预留必须有过期时间 | 防预留泄漏 |

### 7.4 质量追溯

| # | 规则 | 原因 |
|---|---|---|
| R27 | 质检点工序报满后进 `WAIT_INSPECTION` | 门禁状态的载体 |
| R28 | 质检合格或让步接收才放行 | 返工/不合格不能流转 |
| R29 | 质检结果四态（含让步接收/返工） | 二元状态无法表达真实业务 |
| R30 | 物料批次必须记录供应商 | 追溯的终点 |
| R31 | 领料明细必须记录批次号 | 追溯链路的关键一环 |
| R32 | 批次关系必须与领料在同一事务 | 否则追溯链会断 |
| R33 | 追溯必须防环 + 限制深度 | 防死循环与查询爆炸 |

## 9. 非功能性要求

| 维度 | 要求 | 本项目达成情况 |
|---|---|---|
| 一致性 | 库存强一致（单库事务） | ✅ 条件更新 + 本地事务 |
| 一致性 | 跨服务最终一致 | ✅ outbox（MQ 未端到端验证） |
| 并发 | 库存不超发 | ✅ 100 并发实测零超发 |
| 幂等 | 报工/领料/消息消费 | ✅ 三种幂等均验证 |
| 可观测 | 失败可发现 | ✅ 日志 + traceId + outbox 告警 |
| 可测试 | 核心逻辑可单测 | ✅ 127 个单测 |
| 可部署 | 一键启动 | ⚠️ Compose 文件已写但未实跑 |
| 安全 | 密码不可逆 | ✅ BCrypt |
| 安全 | 无状态鉴权 | ✅ JWT |
| 安全 | 统一鉴权入口 | ✅ 网关 |

## 10. 已知限制汇总

| # | 限制 | 影响 |
|---|---|---|
| 1 | 单层 BOM 展开 | 不支持多级 MRP |
| 2 | 人工指定计划，无产能校验 | 不做 APS |
| 3 | 单工厂单仓库 | 无多仓调拨 |
| 4 | 质检与工序跨服务 | 无分布式事务（用状态协同） |
| 5 | 无接口级 RBAC | 角色未用于接口拦截 |
| 6 | 定时任务无分布式锁 | 多实例会重复执行 |
| 7 | MQ/Redis/Nacos/Docker 未端到端验证 | 环境限制 |
| 8 | 无前端界面 | 用 Knife4j 演示 |
| 9 | 无覆盖率量化 | 未接 JaCoCo |
