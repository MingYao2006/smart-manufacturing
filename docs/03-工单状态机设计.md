# 工单状态机设计

> 对应需求文档第 3 周任务 3.4 / 第 5 部分难点 7。
> 本文档记录**实际实现**，并附**真实测试结果**。

---

## 1. 为什么需要状态机

工单有 8 个状态，状态之间的流转有严格业务规则：

- 草稿不能直接下达（必须先审核）
- 未下达的工单不能开工
- 已完工的工单不能取消
- 终态（已关闭/已取消）不能再流转

如果写成 `if-else`：

```java
// ❌ 反例：加一个状态要改 5 处，且容易漏
if (status == DRAFT && target == APPROVED) { ... }
else if (status == APPROVED && target == RELEASED) { ... }
else if (status == RELEASED && target == IN_PROGRESS) { ... }
// ... 还有 N 个分支，且每个入口都要重复一遍
```

问题：
1. **加状态要改多处**，容易漏
2. **校验逻辑散落**，不同入口可能不一致
3. **无法统一加日志/副作用**

## 2. 四层设计

### 2.1 第一层：状态枚举

```java
public enum ProductionOrderStatus {
    DRAFT(1, "草稿"),
    APPROVED(2, "已审核"),
    RELEASED(3, "已下达"),
    IN_PROGRESS(4, "生产中"),
    PAUSED(5, "暂停"),
    COMPLETED(6, "已完工"),
    CLOSED(7, "已关闭"),
    CANCELLED(8, "已取消");

    private final int code;
    private final String desc;
}
```

状态码设计说明：
- **从 1 开始连续编号**（而非 0 或跳号），便于数据库存储与前端下拉
- 状态码**一旦发布不可变更**（历史数据依赖），新增状态只能追加新码

### 2.2 第二层：迁移表（核心）

```java
private static final Map<ProductionOrderStatus, Set<ProductionOrderStatus>> TRANSITIONS;

static {
    Map<ProductionOrderStatus, Set<ProductionOrderStatus>> m = new EnumMap<>(ProductionOrderStatus.class);
    m.put(DRAFT,       EnumSet.of(APPROVED, CANCELLED));
    m.put(APPROVED,    EnumSet.of(RELEASED, CANCELLED));
    m.put(RELEASED,    EnumSet.of(IN_PROGRESS, CANCELLED));
    m.put(IN_PROGRESS, EnumSet.of(PAUSED, COMPLETED, CANCELLED));
    m.put(PAUSED,      EnumSet.of(IN_PROGRESS, CANCELLED));
    m.put(COMPLETED,   EnumSet.of(CLOSED));
    m.put(CLOSED,      EnumSet.noneOf(ProductionOrderStatus.class));
    m.put(CANCELLED,   EnumSet.noneOf(ProductionOrderStatus.class));

    // 包装为不可变，防止运行时被误改
    Map<ProductionOrderStatus, Set<ProductionOrderStatus>> ro = new EnumMap<>(ProductionOrderStatus.class);
    m.forEach((k, v) -> ro.put(k, Collections.unmodifiableSet(v)));
    TRANSITIONS = Collections.unmodifiableMap(ro);
}
```

**为什么用 `EnumMap` + `EnumSet`**：
- `EnumMap` 内部用数组，比 `HashMap` 快且省内存
- `EnumSet` 用位运算，`contains` 是 O(1)
- 都是枚举专用集合，不会误放其他类型

**为什么包装成不可变**：迁移表是全局共享的"规则"，一旦被某处代码误改，整个系统状态判断就错了。

### 2.3 第三层：统一流转入口 + CAS

**所有状态变更必须走同一个方法**：

```java
@Transactional(rollbackFor = Exception.class)
public OrderVO transit(Long orderId, ProductionOrderStatus target, String reason) {
    // 1. 查当前状态
    ProductionOrder order = getOrderEntity(orderId);
    ProductionOrderStatus current = ProductionOrderStatus.of(order.getStatus());

    // 2. 内存校验迁移合法性（快速失败，不浪费数据库连接）
    current.checkTransitTo(target);

    // 3. CAS 更新（数据库兜底，防并发）
    int affected = orderMapper.updateStatusCas(orderId, target.getCode(),
                                               current.getCode(), operatorId);
    if (affected != 1) {
        throw new BusinessException(ErrorCode.CONCURRENT_CONFLICT,
            "工单状态已变更（当前可能已不是[" + current.getDesc() + "]），请刷新后重试");
    }

    // 4. 记录状态流转日志（同一事务）
    statusLogMapper.insert(OrderStatusLog.of(orderId, order.getOrderNo(),
            current, target, reason, operatorId, operatorName));

    // 5. 处理副作用（同一事务内）
    handleSideEffects(order, current, target);

    return toVO(getOrderEntity(orderId));
}
```

对应 SQL：

```sql
UPDATE production_order
SET status = #{target}, update_by = #{operatorId}, update_time = NOW()
WHERE id = #{orderId}
  AND status = #{expected}       -- 🔑 CAS 前置条件
  AND is_deleted = 0
```

### 2.4 第四层：副作用集中处理

```java
private void handleSideEffects(ProductionOrder order, ProductionOrderStatus from,
                               ProductionOrderStatus target) {
    switch (target) {
        case RELEASED -> {
            // 下达：按快照 routeId 展开工序任务（同步、幂等）
            int created = workTaskService.generateTasks(order);
            log.info("[工单下达] orderNo={} 生成工序任务 {} 条", order.getOrderNo(), created);
        }
        case IN_PROGRESS -> orderMapper.markActualStart(order.getId());
        case COMPLETED   -> orderMapper.markActualEnd(order.getId());
        case CANCELLED   -> workTaskService.cancelTasks(order);
        default -> { /* CLOSED / PAUSED / APPROVED 无副作用 */ }
    }
}
```

**为什么集中**：
- 加新状态时，一眼能看出"要处理什么副作用"
- 副作用与状态变更在**同一事务**，不会出现"状态变了但任务没生成"
- 便于测试

## 3. 并发安全：为什么必须 CAS

### 3.1 问题场景

工单状态会被**多个入口并发修改**：

| 入口 | 触发时机 |
|---|---|
| 人工操作 | 计划员点"下达" |
| 报工消息消费者 | 所有工序完成后自动完工 |
| 定时兜底任务 | 修复"工序全完成但工单未完工" |
| 取消接口 | 计划变更时取消 |

### 3.2 先查后改的经典 bug

```
时刻   线程 A（下达）              线程 B（取消）
t1     读 status = APPROVED
t2                               读 status = APPROVED
t3     校验 APPROVED→RELEASED ✅
t4                               校验 APPROVED→CANCELLED ✅
t5     UPDATE status = RELEASED
t6                               UPDATE status = CANCELLED  ← 覆盖了 A 的结果
```

结果：工单被取消，但工序任务已经生成了 → **数据不一致**。

### 3.3 CAS 如何解决

```sql
-- 线程 A
UPDATE production_order SET status=3 WHERE id=1 AND status=2;  -- 影响 1 行 ✅
-- 线程 B（此时 status 已是 3，不是 2）
UPDATE production_order SET status=8 WHERE id=1 AND status=2;  -- 影响 0 行 ❌
```

线程 B 拿到影响行数 0 → 抛 `CONCURRENT_CONFLICT(40902)` → 前端提示"状态已变更，请刷新"。

**关键点**：
- 判断与更新在**同一条 SQL**，中间没有窗口期
- 数据库行锁天然保证互斥，**不需要应用层加锁**
- 影响行数直接给出成功/失败信号
- **不需要重试循环**（库存需要"要么够要么不够"，工单状态是"要么能要么不能"）

### 3.4 为什么影响行数必须严格 `== 1`

```java
if (affected != 1) { throw ... }   // ✅ 正确
if (affected <= 0) { throw ... }   // ⚠️ 危险
```

如果写成 `<= 0`：万一 SQL 因某种原因影响了多行（如 `WHERE` 条件写漏了 `id`），
`affected = 5` 也会被判定为"成功"，而实际是灾难。**严格等于 1 是对 SQL 写错的兜底。**

## 4. 状态流转日志

每次流转都写入 `order_status_log`（只增不改）：

| 字段 | 说明 |
|---|---|
| `order_id` / `order_no` | 工单 |
| `from_status` / `from_status_desc` | 原状态（首次创建为 null） |
| `to_status` / `to_status_desc` | 目标状态 |
| `reason` | 操作原因 |
| `operator_id` / `operator_name` | 操作人 |
| `operate_time` | 操作时间 |

**为什么需要**：
- 出问题时能还原"工单经历了什么"
- 客户投诉时能定位"谁在什么时候改了状态"
- 面试时可讲"状态机不仅防非法迁移，还要可追溯"

实测输出（`GET /order/{id}` 的 `statusLogs`）：

```
创建 → 草稿  原因=创建工单
草稿 → 已审核  原因=审核通过
已审核 → 已下达  原因=工单下达
已下达 → 生产中  原因=
生产中 → 已完工  原因=所有工序已完成，自动完工
```

## 5. 工序任务状态机（含质检门禁）

### 5.1 迁移表

```
PENDING         → IN_PROGRESS, SKIPPED
IN_PROGRESS     → PAUSED, COMPLETED, WAIT_INSPECTION
PAUSED          → IN_PROGRESS
WAIT_INSPECTION → COMPLETED（质检合格放行）, IN_PROGRESS（质检不合格返工）
COMPLETED       → （终态）
SKIPPED         → （终态）
```

### 5.2 两个关键状态

| 状态 | 为什么需要 |
|---|---|
| `WAIT_INSPECTION` | `is_inspection=1` 的工序报工完成后**不是直接完成**，而是先等质检。如果只有 `COMPLETED`，质检门禁就形同虚设 |
| `PAUSED` | 设备故障、换料、交接班都会暂停。没有暂停状态，工人只能"假装没开始"或"假装已完成"，**数据就失真了** |

### 5.3 质检门禁的完整链路

```
工序报满 100 件（is_inspection=1）
  → 状态 IN_PROGRESS → WAIT_INSPECTION
  → 后道工序尝试开始 → 校验前道状态 ≠ COMPLETED → 拒绝 40906
  → 录入质检单 result=1（合格）
  → POST /work-task/{id}/pass-inspection
  → 状态 WAIT_INSPECTION → COMPLETED
  → 后道工序可以开始
```

**实测结果**：
```
质检点工序状态: 待质检
✓ 质检点报满后进入【待质检】而非【已完成】
✓ 前道质检未放行时，后道不能开始（工艺纪律）（返回 40906）
质检单: QC20261031001096400 结果=合格
```

### 5.4 工序顺序约束（工艺纪律）

**实现要点**：取"所有 `step_no` 小于当前的最大那条"，而不是 `step_no - 10`。

```sql
-- ✅ 正确：工序号可能不连续（10/20/30，插入 15 后仍正确）
SELECT * FROM work_task
WHERE order_id = ? AND step_no < ? AND is_deleted = 0
ORDER BY step_no DESC LIMIT 1

-- ❌ 错误：假设工序号步长固定为 10
WHERE step_no = ? - 10
```

**为什么这个细节重要**：工序号设计成 10/20/30 就是为了留插入空间。
如果按"减 10"去算，插入 15 后所有判断都会错。

**前道允许的"完成"状态**：`COMPLETED` 或 `SKIPPED`（跳过也是合法终态）。

## 7. 加一个新状态要改几处？

**答案：3 处**

| # | 位置 | 改动 |
|---|---|---|
| 1 | `ProductionOrderStatus` 枚举 | 加一个枚举值 |
| 2 | `TRANSITIONS` 静态块 | 加它的出边 + 其他状态指向它的边 |
| 3 | `handleSideEffects` switch | 如果它有副作用，加一个 case |

**对比 if-else 写法**：至少改 5~10 处（每个入口的 if 链 + 校验 + 日志），且极易漏。

> 这也是面试高频追问："你的状态机加一个新状态要改几处？"—— 3 处，且都不在业务代码里。

## 8. 与其他方案对比

| 方案 | 优点 | 缺点 | 本项目 |
|---|---|---|---|
| if-else 硬编码 | 直观 | 加状态改多处、易漏、难测试 | ❌ |
| Spring StateMachine | 功能全（分层状态、持久化、事件） | 重、学习成本高、本项目状态机很简单 | ❌ 过度设计 |
| **枚举 + 迁移表 + 统一入口 + CAS** | 轻量、集中、可测、并发安全 | 无可视化（可画文档补） | ✅ |
| 数据库配置化状态机 | 不改代码就能改流程 | 规则外置后难以静态检查，复杂度高 | ❌ |

**选型理由**：本项目状态机是**固定业务规则**（制造业工单流程变化很少），
用编译期可检查的枚举 + 迁移表比"配置化"更安全。
`Spring StateMachine` 对 8 个状态的场景是明显过度设计。
