### 2.4 测试中发现并修复的真实缺陷

#### 缺陷 1：追溯深度截断时返回空树

| 项 | 内容 |
|---|---|
| **现象** | `testMaxDepthTruncation` 失败：`expected: <1> but was: <0>`（结果树为空） |
| **原因** | `walk()` 在到达 `maxDepth` 时直接 `break`，**未把本层节点加入 `visited`**；<br/>`buildTree()` 因 `!visited.contains(childId)` 把这些节点全部跳过 |
| **影响** | `maxDepth=1` 时用户看到"没有任何上游"，与事实不符（有 1 层，只是被截断） |
| **修复** | 到达深度上限时先 `walk.visited.addAll(nextLevel.keySet())` 再 break |
| **状态** | ✅ 已修复，测试通过 |

#### 缺陷 2：环形批次数据导致 StackOverflow

| 项 | 内容 |
|---|---|
| **现象** | `testCycleDetection` 抛 `StackOverflowError` |
| **原因** | `childrenOf` 的父子关系在数据有环时形成 A→B→A 循环引用；<br/>`buildTree()` 递归时没有"已输出"防护 |
| **影响** | 生产环境若存在脏数据（人工录入错误、迁移遗留），**整个追溯接口会被打挂** |
| **修复** | `buildTree()` 增加 `emitted` 集合，已输出的批次不再重复展开 |
| **状态** | ✅ 已修复，测试通过 |

> 这两个缺陷都只在**边界条件**下暴露（深度截断、异常数据），
> 正常流程测试完全不会发现 —— **这正是单元测试的价值所在**。

### 3.5 场景四：库存对账

```

→ {"code":0,"message":"对账通过，未发现异常","data":0}
```

对账校验四项：
1. `inventory.quantity` vs `SUM(流水.quantity)` — 现有量
2. `inventory.reserved_quantity` vs `SUM(预留表.reserved - issued)` — 预留量
3. 负值检测
4. 预留量 ≤ 现有量

> **开发中发现的真实设计缺口**：
> 初始化库存时只写 `material_inventory` 不写流水 → 对账报 10 条 `QUANTITY_DIFF`。
> 这不是 bug，而是**对账在正确地发现"账实不符"**。
> 修复：`sql/06_init_data.sql` 增加"期初入库"流水（`transaction_type=1`）。
> **这条记录现在保证了 `SUM(流水) == 库存表`，后续任何偏差才是真异常。**

### 为什么不做 JMeter 压测（诚实表述）

计划书明确要求：

> **不要写"我的系统支持 10000 QPS"** —— 学生项目在笔记本上跑不出可信的 QPS，写了反而被质疑。
> 正确表述："在本地环境 50 并发下错误率 0%，库存数据一致性正确"

本项目选择了**更聚焦的目标**：验证**并发正确性**（零超卖、账实一致），
而不是刷 QPS 数字。这比一个漂亮但不可复现的 QPS 数字有价值。

## 7. 结论

### 7.1 已验证的能力

| 能力 | 证据 |
|---|---|
| **并发不超卖** | 100 并发 → 100 成功 0 失败，available=0；50 库存 → 恰好 50 成功 |
| **事务回滚正确** | 3 物料中途失败 → 前 2 个 reserved 归 0，预留记录 0 条 |
| **状态机正确** | 60 个单测覆盖工单+工序状态机全部合法迁移与 30 条非法迁移 |
| **快照正确** | 工单锁定 bomId/routeId，端到端断言一致 |
| **损耗率计算正确** | 7 种物料全部与手工核算一致 |
| **防超报正确** | 并发条件更新 + 单测 + 端到端三重验证 |
| **幂等正确** | 报工单号、领料单号、进度重算三种幂等均验证 |
| **质检门禁生效** | 待质检状态 + 后道被拒 40906 + 放行后才可继续 |
| **追溯正确** | 正反向、多层、带供应商；环路不死循环；深度截断有标记 |
| **账实一致** | 对账 0 异常（库存表 = 流水累加 = 预留表推算） |
| **鉴权生效** | 无 token → 401；token 可解析出正确身份 |

### 7.2 已知缺口

1. MQ / Redis / Nacos / Docker 的端到端验证（环境限制）
2. 接口级 RBAC 未接入
3. 前端页面未做
4. 覆盖率未量化（未接 JaCoCo）
5. 批量/大数据量性能未测

### 7.3 项目质量的自我评价

**做得好的**：
- 核心业务逻辑（状态机、库存并发、追溯）**做到了正确性可验证**，不是"看起来能跑"
- **单测抓到了 2 个真实 bug**（深度截断空树、环路 StackOverflow），说明测试有效
- 并发测试**跑出了真实数据**，且断言严格（恰好 100 次成功，不是"大约"）
- 文档如实标注了边界与未验证项

**做得不够的**：
- 消息可靠性的代码完整但**未做真实 MQ 验证** —— 这是最大的缺口
- 没有前端，演示体验受限
- 定时任务的真实触发未验证

> **诚实比完美更重要。** 一个跑得通、讲得清、有真实测试数据的项目，
> 胜过一个功能列表很长但处处半成品、经不起追问的项目。
