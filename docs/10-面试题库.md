# 面试题库（45 题，含答案要点）

> 每题都要准备"**为什么这样设计、不这样会怎样**"。
> 只准备"是什么"会被追问穿；能讲清"为什么不用"才是真理解。

## A. 业务理解（8 题）

### 1. MES 是什么？它和 ERP 的边界在哪？

**答案要点**：
- MES = Manufacturing Execution System，制造执行系统，管**车间执行层**
- ERP 管计划、采购、销售、财务，时间粒度是天/周/月；MES 管工单、工序、报工、质量、追溯，粒度是**分钟/小时**
- 边界：ERP 告诉我"这个月要生产 10000 台"，MES 回答"今天这台产线上谁在做哪道工序、做了多少、合不合格、用的哪批料"
- **我做的项目明确只做执行层，不做计划与成本**

### 2. 离散制造和流程制造有什么区别？你的系统支持哪种？

**答案要点**：
- 离散制造：产品可拆分成零件（电子、机械、汽车），BOM 是**装配关系**
- 流程制造：物料形态连续变化（化工、冶金、食品），需要**配方版本、罐批追踪、联副产品**
- **我只做离散制造**。因为流程制造的批次管理是"罐"级别的混合，还有配方版本与产出率问题，业务模型完全不同
- 明确知道边界比假装全能更加分

### 3. 什么是 BOM？为什么 BOM 要版本化？

**答案要点**：
- BOM（Bill of Materials）定义"一个产品由哪些物料按什么用量组成"
- **版本化原因**：
  1. **追溯要求**：三个月前的工单，必须能查到当时用的是哪个 BOM 版本
  2. **变更控制**：BOM 变更要走流程（草稿→审核→生效），不能直接改
  3. **并行生产**：老工单用 V1，新工单用 V2，必须能同时存在
- 具体规则：同一产品同时只能有一个生效版本；已生效的不允许改明细，要改必须新建版本

### 4. 什么是工艺路线？它和 BOM 是什么关系？

**答案要点**：
- 工艺路线（Routing）定义"这个产品要经过哪些工序、在哪个工作中心、标准工时多少、哪些是质检点"
- 与 BOM 的关系：**BOM 是"用什么做"，工艺路线是"怎么做"，两者是并列的"两套配方"**
- 都挂在同一产品上，都版本化，都要求"同产品唯一生效"
- 工序任务（work_task）就是工艺路线的执行实例

### 5. 什么是工单？工单和计划是什么关系？

**答案要点**：
- 工单（Work Order）是"一次具体的生产任务"，所有执行动作都挂在工单下
- 计划与工单是 **1:N**：一个 1000 件的计划可以拆成多个批次（每次 200 件），因为设备/物料/人力限制
- 工单必须**快照** BOM 和工艺路线版本（这是核心设计）

### 6. 为什么要做物料预留？不做会怎样？

**答案要点**：
- 不做预留的两种情况都出问题：
  - **创建工单就扣库存**：工单取消要退回；长期不生产库存被占死
  - **领料时才扣库存**：两个工单同时认为库存够用 → 超发
- 预留 = 先锁定（`reserved_quantity += N`），领料时才实扣（`quantity -= N, reserved -= N`）
- 两段式既防超发又不提前扣账

### 7. 什么是批次追溯？为什么制造业必须有？

**答案要点**：
- 批次追溯 = 通过批次号建立"原料批次 → 产品批次"的关系链，支持正反向查询
- 三个真实需求：
  1. **质量事故召回**：某供应商芯片有缺陷 → 查出所有用了它的成品 → **精准召回而非全部召回**
  2. **客诉定位**：客户投诉某台电表 → 查出用了哪些料、哪个供应商、谁做的
  3. **合规**：汽车/医疗/电子行业强制要求
- 这是 MES 最有辨识度的能力，也是区别于普通 CRUD 系统的核心

### 8. 你的系统能支持多工厂吗？为什么不能？

**答案要点**：
- 不能。当前设计是单工厂单车间：
  - `warehouse_id` 已建模但固定为 1
  - 组织维度没有做（工厂→车间→产线→工作中心只有 `work_center` 一个字符串字段）
  - 跨组织的数据隔离、权限、计划协同都没做
- 如果要支持，需要加组织维度、数据权限、多仓调拨、跨厂计划协同
- **明确说不支持，并说清为什么，比含糊其辞好**

## B. 库存与并发（8 题）

### 9. 库存三量模型是什么？为什么可用量不存字段？

**答案要点**：
- `quantity`（现有量）— 仓库实际有多少
- `reserved_quantity`（预留量）— 被工单锁定但未领走
- 可用量 = `quantity - reserved_quantity` — **计算值，不存字段**
- 不存字段的原因：如果存三个字段，就可能出现"70 ≠ 100 - 30"的不一致（某处代码只更新了两个）。这类不一致在生产环境极难排查，而**计算值永远不会自相矛盾**

### 10. 如何保证高并发下不超卖？

**答案要点**：
- 用**数据库条件更新（CAS）**：把判断写进 WHERE

```sql
UPDATE material_inventory
SET reserved_quantity = reserved_quantity + #{qty}
WHERE material_id = #{materialId}
  AND warehouse_id = #{warehouseId}
  AND quantity - reserved_quantity >= #{qty}
```

- 判影响行数：1 成功，0 可用量不足
- **实测数据**：100 线程并发预留 100 库存，恰好 100 次成功、0 次失败，最终 `available = 0`，无负数
- 超出场景：100 线程抢 50 库存 → 恰好 50 成功 50 失败，预留记录 50 条（账实一致）

### 11. 为什么不用 Redis 分布式锁做库存扣减？

**答案要点**（这题很能体现深度）：
- **Redis 锁只能保证互斥，不能保证"锁内读到的数据仍然有效"**
- 典型流程：加锁 → 查库存 → 判断 → 更新 → 解锁。锁内查完库存后，数据可能已被其他事务修改
- 而且引入 4 个新故障点：锁超时、看门狗续期、主从切换丢锁、误删他人锁
- 条件更新的优势：判断与更新在**同一条 SQL**，无窗口期；数据库行锁天然互斥；无额外组件
- **结论：不是 Redis 锁不能用，而是这个场景用了反而更差**
- 补充：Redis 锁在本项目有更合适的用途 —— **定时任务防多实例重复执行**

### 12. 条件更新和乐观锁有什么区别？各适合什么场景？

**答案要点**：

| | 条件更新（CAS） | 乐观锁（version） |
|---|---|---|
| 判断依据 | **业务条件**（`quantity - reserved >= qty`） | 版本号（`version = expected`） |
| 失败含义 | **业务失败**（库存不够） | **并发冲突**（数据被改过） |
| 处理方式 | 直接返回失败，不重试 | 通常需要重试 |
| 适合 | 库存这种"要么够要么不够" | 冲突少、可重试的场景（如编辑表单） |

- 库存是**热点行**，乐观锁冲突率高 → 大量重试放大数据库压力
- 而且库存业务"不够就是不够"，重试没意义

### 13. 多个物料同时预留怎么防死锁？

**答案要点**：
- **按 `material_id` 升序排序后依次预留**，保证所有事务的加锁顺序一致
- 原理：事务 A 锁物料 1 再锁 2，事务 B 也先锁 1 再锁 2 → 不会循环等待
- 如果顺序相反（A: 1→2，B: 2→1）就会死锁
- 代码里用 `sorted(Comparator.comparing(RequirementItem::getMaterialId))`
- **单测验证**：故意倒序传入两个物料，断言实际调用顺序是升序

### 14. 预留和实际扣减有什么区别？为什么要分两段？

**答案要点**：
- **预留**：只动 `reserved_quantity`，`quantity` 不变（物料还在仓库）
- **领料（实扣）**：`quantity -= N` **且** `reserved_quantity -= N`（物料离开仓库）
- 分两段的原因：预留解决"锁料防超发"，实扣解决"物料实际出库"。合并成一步会有开头第 6 题的问题

### 15. 预留泄漏怎么处理？

**答案要点**：
- 预留泄漏 = 工单取消或长期不生产，预留没释放 → 库存被永久锁死
- **三重兜底**：
  1. 工单取消时主动释放（状态机 `CANCELLED` 副作用）
  2. `material_reservation.expire_time` 预留过期时间（默认 7 天）
  3. 定时任务每天 02:00 扫过期预留释放
- 释放用条件更新 `WHERE reserved_quantity >= qty`，保证幂等（不会减成负数）

### 16. 如何验证你的库存并发方案是正确的？

**答案要点**：
- 写并发测试程序（`CountDownLatch` 让所有线程**同时**发起请求）
- 三个场景：
  1. 库存 100 + 100 线程各预留 1 → **恰好 100 成功、0 失败**，`available = 0`
  2. 库存 50 + 100 线程 → **恰好 50 成功、50 失败**，无负数，预留记录 50 条
  3. 3 物料中途失败 → 前 2 个 `reserved` **归 0**，预留记录 0 条
- 再加对账：库存表 vs 流水累加 vs 预留表推算，结果 0 异常
- **强调"不修改测试来迁就代码"** —— 测试失败就是发现 bug

## C. 状态机与事务（7 题）

### 17. 工单状态机怎么设计的？为什么不用 if-else？

**答案要点**：
- **四层**：状态枚举 + 迁移表（`EnumMap<Status, Set<Status>>`）+ 统一流转入口 + 副作用集中处理
- if-else 的问题：
  - 加一个状态要改 5~10 处（每个入口的 if 链 + 校验 + 日志）
  - 校验逻辑散落，不同入口可能不一致
  - 无法统一加日志/副作用
- 迁移表的好处：**加状态只改一处**，一处定义全局生效

### 18. 状态流转如何保证并发安全？

**答案要点**：
- **CAS 条件更新**：`UPDATE ... SET status=? WHERE id=? AND status=?`
- 判影响行数必须**严格等于 1**，否则抛 `CONCURRENT_CONFLICT(40902)`
- 为什么不能只靠内存校验：工单状态会被多入口并发修改（人工操作、报工消息、定时任务）。先查后改必然覆盖
- 为什么严格等于 1 而非 `> 0`：防止 SQL 写漏 `id` 条件时误判成功

### 19. 状态机的非法迁移怎么拦截？

**答案要点**：
- 内存层：`checkTransitTo()` 查迁移表，非法直接抛 `STATE_TRANSITION_DENIED(40901)`
- 数据库层：CAS 的 `WHERE status = expected` 也会拦住（如果状态已被改）
- 两层配合：内存层是快速失败（省数据库连接），数据库层是并发防线
- **测试证据**：36 个单测覆盖 12 条合法迁移（100%）+ 18 条非法迁移

### 20. 为什么工单要快照 BOM 和工艺路线版本？

**答案要点**（面试必问）：
- 如果只存 `product_id`，查物料需求时要用"产品当前生效 BOM"
- 但 BOM 可能已升级到 V2 → **正在生产的工单物料需求莫名变了** → 备料算错 → 停产
- 存 `bom_id` 后，工单创建那一刻就"拍照"，之后 BOM 怎么改都不影响它
- **这是制造业铁律**：历史工单的物料需求必须可追溯、可解释
- 实测：V2 生效后，旧工单的 `bomId` 仍是 V1 的 id

### 21. 跨服务操作如何保证一致性？

**答案要点**：
- **按场景分级，不滥用分布式事务**：

| 场景 | 方案 |
|---|---|
| 工单状态变更 + 生成工序任务（同服务） | 本地事务 |
| 报工 + 更新工单进度（跨服务） | **本地消息表 + 最终一致** |
| 工单下达 + 物料预留（跨服务） | 状态机 + 补偿（预留失败 → 工单置下达失败） |
| 质检合格 + 工序流转 | 状态机门禁（`WAIT_INSPECTION`），不做分布式事务 |

### 22. 为什么不用 Seata？

**答案要点**：
- **可用性优先于强一致**，这是制造业系统的正确取舍
- Seata AT 的问题：TC 单点，挂了全链路阻塞；全局锁导致吞吐下降；引入 undo_log 复杂度
- MES 的业务节奏是**分钟级**，不是秒杀。允许"工单下达后工序任务延迟 1 秒生成"，不允许"因为 TC 挂了整条产线无法下达工单"
- 用本地消息表 + 定时补偿，没有单点

### 23. 什么是中间态？为什么需要它？

**答案要点**：
- 中间态 = 跨服务操作的"进行中"状态（如工单的 `RELEASING`）
- 为什么需要：没有中间态，系统只有"成功/失败"两种，跨服务操作一旦中断就**无法判断到底做没做**
- 有了中间态：可以表达"部分完成"，可以由定时任务检查并恢复（已完成 → 推进到成功；未完成 → 重试或置失败）
- 本项目的实践：工序的 `WAIT_INSPECTION` 也是一种中间态（做完了但没放行）

## D. 消息与幂等（8 题）

### 24. 消息可能在哪些环节丢失？怎么解决？

**答案要点**：
- **三个环节**：①生产者发送丢失 ②Broker 宕机丢失 ③消费失败丢失
- 三端加固：
  - ① **本地消息表 outbox**：业务数据与消息记录同一事务写入；定时投递 + 等 publisher confirm
  - ② 交换机/队列/消息**持久化** + 死信交换机
  - ③ 消费重试 + 耗尽进死信 + `default-requeue-rejected=false` 防毒消息

### 25. 为什么必须等 publisher confirm？不等会怎样？

**答案要点**：
- `rabbitTemplate.send()` 只是把字节写进 **TCP 缓冲区**，不代表 Broker 收到了
- 如果不等 confirm 就标记"已投递"，网络抖动时消息实际丢了但系统认为成功 → **静默丢失**
- 只有 confirm 的 ack 才能证明消息进了 Broker
- 用 `CorrelationData.getFuture().get(timeout)` 同步等待

### 26. 本地消息表的原理是什么？如何保证不丢？

**答案要点**：
- 原理：把"要发的消息"当成一条**记录**，和业务数据在**同一事务**里写入 outbox 表
- 事务提交 → 消息记录一定在库里 → 定时任务扫出来投递
- 即使发 MQ 前进程崩溃，重启后定时任务仍会补发
- 幂等写入：`INSERT IGNORE` + 唯一索引 `uk_outbox_biz(biz_key, exchange_name)` 保证同一业务事件只写一条
- 状态机：0 待投递 → 1 已投递 / 2 失败（终态告警）/ 3 路由退回

### 27. 消息重复消费怎么处理？

**答案要点**：
- MQ 是 **at-least-once** 语义，重复是必然的
- 两种方式：
  - **重算**（优先）：进度 = `SUM(报工)`，而不是 `+= 增量`。算几次结果一样
  - **去重**（有副作用时）：Redis SETNX 或数据库唯一索引
- 本项目用**重算**：`recalculateProgress` 是幂等运算
- **实测**：重复重算一次，`completed_quantity` 保持 300.0 不翻倍

### 28. 幂等的两种实现方式？各适合什么场景？

**答案要点**：

| 模式 | 原理 | 适合 |
|---|---|---|
| **去重（SETNX/唯一索引）** | 处理前占位，占不到就跳过 | 有副作用的操作（加余额、发通知） |
| **重算（幂等运算）** | 结果由数据推导 | 汇总类数据（进度、统计） |

- **优先用重算**：不依赖 Redis（少一个故障点）、无键过期问题、消息丢了也能靠定时兜底自愈

### 29. 为什么幂等键失败后要释放？

**答案要点**（这题很能体现严谨）：
- **幂等键只能挡住"该跳过的重复"，不能挡死"该重试的失败"**
- 如果不释放：第一次消费失败 → 键还在 → 重投时被挡住 → 数据永远补不回来
- 所以要在 catch 里 `redisTemplate.delete(key)` 再抛异常
- 更好的做法：把幂等记录写在**业务事务内**（用数据库唯一索引），失败回滚时记录一起回滚，天然不会挡死重试

### 30. 为什么"重算"比"累加"更适合进度类数据？

**答案要点**：
- 累加：`order.completed += qty` → 重复消费就多加一次 → 进度超 100%
- 重算：`order.completed = SUM(report.qualified)` → 算几次都一样
- 额外好处：**数据自愈**。即使 MQ 丢消息，定时任务重算一次就能把进度修正
- 代价：多一次聚合查询（可接受，因为报工是低频操作）

### 31. 消息路由失败（到了交换机但没队列）怎么发现？

**答案要点**（这题是加分项）：
- 这是最隐蔽的坑：Broker **确实收到了**消息（所以 confirm 返回 ack），但**找不到匹配队列，消息被丢弃**
- 如果不处理，outbox 被标记"已投递"，实际无人接收 → 静默丢失
- 解决：开 `publisher-returns: true` + `template.mandatory: true`，处理 `setReturnsCallback`，把 outbox 重置为待投递
- **能讲出这个坑，说明真的踩过或想清楚了**

## E. 追溯与质量（5 题）

### 32. 批次追溯的数据结构是什么？为什么是图不是树？

**答案要点**：
- 是**有向无环图（DAG）**：`product_batch` 是节点，`batch_relation` 是边
- 为什么不是树：
  - 一个物料批次可用于多个产品批次（1:N）
  - 一个产品批次消耗多个物料批次（N:1）
  - ⇒ 多对多
- 如果建模成树，无法表达"一个芯片批次影响了 2 个成品"—— 而这恰恰是召回场景的核心

### 33. 正向追溯和反向追溯分别怎么实现？

**答案要点**：

| | 反向追溯 | 正向追溯 |
|---|---|---|
| 输入 | 产品批次号 | 物料批次号 |
| 遍历 | 沿 `source_batch_id` 向上（BFS） | 沿 `target_batch_id` 向下（BFS） |
| 分组键 | 按 `target_batch_id` 分组 | 按 `source_batch_id` 分组 |
| 输出 | 上游物料批次 + **供应商** | 下游产品批次 |
| 业务 | 客诉定位根因 | 质量事故精准召回 |

- 实现要点：一次查出全部边，内存 BFS（避免 N+1）

### 34. 追溯如何防止死循环？

**答案要点**：
- 用 `visited` 集合记录已访问节点，已访问的不再展开
- **但只靠 visited 不够**：`childrenOf` 的父子关系在数据有环时仍会形成循环引用，`buildTree` 递归会 StackOverflow
- 所以需要**第二层防护**：`buildTree` 里用 `emitted` 集合，已输出的节点不再重复展开
- **这个缺陷是我单测发现的**（`testCycleDetection` 一开始抛 StackOverflow）
- 另外还要限制最大深度（默认 10 层）

### 35. 质检如何与工序流转联动？

**答案要点**：
- `process_step.is_inspection = 1` 的工序是质检点
- 报满后**不是直接 COMPLETED**，而是进入 `WAIT_INSPECTION`
- 后道工序开始时校验前道状态必须 `COMPLETED`/`SKIPPED`，`WAIT_INSPECTION` 被拒绝（40906）
- 质检合格或让步接收 → `WAIT_INSPECTION → COMPLETED`，后道才能开始
- 质检不合格/返工 → `WAIT_INSPECTION → IN_PROGRESS`（退回返工）
- 实测验证：`40906 前道工序[20-老化测试]当前状态为[待质检]，未完成`

### 36. 质检结果为什么要有"让步接收"和"返工"？

**答案要点**：
- 二元状态（合格/不合格）无法表达真实业务：
  - **让步接收**：轻微不良但客户同意放行（很常见）
  - **返工**：可修复，退回工序重新加工
  - **不合格**：不可修复，报废
- 不同结果对应**不同的后续动作**（放行 / 返工 / 报废），如果只有二元状态，业务没法表达
- **能说出"让步接收"这个词，比会写 CRUD 更能体现制造业业务理解**

## F. 工程化与架构（9 题）

### 37. 为什么拆成 5 个服务而不是 8 个？拆分依据是什么？

**答案要点**（核心问题）：
- **拆分依据是事务边界和变更频率，不是名词**
- **process 必须合并进 production**：工序任务是工单的执行视图，报工是工单进度的唯一来源，它们共享同一聚合根和事务边界。拆开后"报工→更新进度"变成跨服务调用 + 分布式事务，而这是每分钟都在跑的高频链路
- **quality 独立但可降级**：有独立业务概念值得建模，但与 production 强同步耦合。时间紧时把表并入 production 用本地事务
- **inventory 必须独立**：技术含量最高（并发、预留实扣、对账），独立才能讲成完整专题
- 8 个服务的脚手架成本也吃掉了本该做业务的时间

### 38. 你的系统有哪些兜底机制？

**答案要点**：
1. **MQ 丢消息** → 定时扫"所有工序终态但工单未完工"的数据重算
2. **outbox 投递失败** → 定时告警 + 手动补偿接口
3. **预留泄漏** → 工单取消释放 + 过期时间 + 定时清理
4. **库存账实不符** → 每日对账（库存表 vs 流水 vs 预留表）
5. **唯一索引兜底** → 工单号/报工单号/领料单号/工序任务并发重复
6. **CAS 兜底** → 状态并发修改
7. **深度限制 + 防环** → 异常数据不会打挂追溯

### 39. 如何做库存对账？发现不一致怎么办？

**答案要点**：
- 四项校验：
  1. `inventory.quantity` vs `SUM(流水.quantity)`
  2. `inventory.reserved_quantity` vs `SUM(预留表.reserved - issued)`
  3. 负值检测
  4. 预留量 ≤ 现有量
- 默认**只记录不自动修正**（自动修正会掩盖真实 bug）
- 差异写入 `inventory_reconcile_log`，人工分析原因
- 需要时可用 `autoFix=true` 以流水为准修正
- **关键认知**：对账的价值不在"修正"，而在**发现**

### 40. 你的系统有哪些已知限制？

**答案要点**（诚实回答，这题很关键）：
1. **单层 BOM 展开**，不做多级 MRP
2. **不做自动排程**（APS）
3. **单工厂单仓库**
4. **质检与工序跨服务**，用状态协同而非分布式事务
5. **无接口级 RBAC**
6. **定时任务未加分布式锁**（单机无影响）
7. **MQ/Redis/Nacos/Docker 未做端到端验证**（环境限制）
8. **无前端界面**
9. **无覆盖率量化**

> 面试官最怕的是"什么都能做"的候选人。**能清晰说出边界的反而更可信。**

### 41. 你的项目里最具技术含量的是什么？

**答案要点**（挑 2 个深入讲）：
1. **库存并发控制**：三量模型 + 条件更新 + 100 并发实测零超卖 + 事务回滚验证
2. **批次追溯 DAG**：图建模 + BFS + 防环 + 深度限制 + 单测抓到 2 个真实 bug
- 备选：状态机（CAS）、消息可靠性（outbox）

### 42. 单测抓到了什么问题？

**答案要点**（能讲出"测试真的有用"）：
- **缺陷 1**：追溯深度截断时返回空树（截断层节点未加入 `visited`）
- **缺陷 2**：环形批次数据导致 `buildTree` 无限递归 StackOverflow
- 这两个都只在**边界条件**下暴露（深度截断、异常数据），正常流程测试不会发现
- **这就是"测试失败就是发现 bug，不要改测试去迁就代码"的实证**

### 43. 为什么测试不用 Mockito？

**答案要点**（体现工程判断）：
- Mockito 默认 MockMaker 通过 ByteBuddy **self-attach** 挂载 Java Agent（需派生外部进程）
- 我的开发环境是受限沙箱，无法派生进程 → 报 `Could not self-attach to current VM`
- 改用 **JDK 动态代理**手写桩（零依赖、零字节码增强）
- 同时按 DIP 重构：抽出 `MessagePublisher` / `ProductCatalogClient` 接口，测试用 Fake 实现
- **好处**：测试不依赖网络/MQ/Redis，127 个用例 1.5 秒跑完；未来换 Feign 也不影响业务代码

### 44. 如果让你继续做，下一步做什么？

**答案要点**（按优先级）：
1. **补 MQ 端到端验证**（装 RabbitMQ，跑重复消费/宕机恢复/死信）—— 最大的缺口
2. **前端 3~4 个核心页面**（工单看板、报工、追溯查询）—— 提升演示体验
3. **接口级 RBAC**（角色已建模，接 `@PreAuthorize`）
4. **定时任务分布式锁**（Redisson 选主）
5. **多级 BOM 展开**（递归 + 提前期）
6. **可观测性**（Prometheus 指标 + SkyWalking 链路）

### 45. 这个项目和真实企业级 MES 的差距在哪？

**答案要点**（诚实）：
- **规模**：单工厂 vs 多工厂多组织
- **功能深度**：无 APS 排程、无设备联网（OEE）、无成本核算、无 SPC 统计过程控制
- **多级 BOM**：只做单层展开
- **工程化**：无 CI/CD、无灰度发布、无完整监控告警
- **数据量**：没有真实大规模数据验证过性能
- **但核心业务模型是真实的**：BOM 版本化、工单快照、预留实扣两段式、批次追溯 DAG、状态机 CAS
  —— 这些是企业 MES 也一模一样的核心设计

## 附：面试中最容易被追问的 5 个点

| 追问 | 准备要点 |
|---|---|
| "你说 100 并发零超发，怎么验证的？" | 说清测试代码（CountDownLatch + 100 线程同时放行）、断言内容（恰好 100 成功 0 失败）、最终数据（available=0，无负数），并说明"不同 orderId 才能打到同一行库存" |
| "为什么不用 Seata？" | 可用性优先 + 业务允许分钟级延迟 + 避免 TC 单点（详见第 22 题） |
| "工单状态机加一个新状态要改几处？" | **3 处**：枚举 + 迁移表 + 副作用 switch（详见 `docs/03-工单状态机设计.md` §7） |
| "消息重复消费你怎么保证只处理一次？" | 优先重算（天然幂等，进度由 SUM 重算而非累加）；有副作用才用 SETNX + **失败释放键** |
| "你的系统和真实 MES 差距在哪？" | 明确说边界：无 APS、无设备联网、无成本核算、单工厂、单层 BOM（详见第 40/45 题） |
