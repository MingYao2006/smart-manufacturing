## 1. 报工：本周最容易做错的地方

### 1.1 报工流程（8 步）

```
① 校验报工单号幂等（已存在 → 直接返回，不重复处理）
② 校验 合格数 + 不良数 = 报工数（服务端校验，前端不可信）
③ 查工序任务，状态必须 IN_PROGRESS
④ 条件更新累加 reported_quantity（防超报，并发安全）
⑤ 插入 production_report（明细账）
⑥ 判断是否报满 → 流转终态（需质检 → WAIT_INSPECTION）
⑦ 同一事务内写 mq_outbox（报工完成事件）
⑧ 事务提交后由定时任务异步投递 → 消费者重算工单进度
```

### 1.2 数量校验必须在服务端

```java
private void validateQuantity(ReportCreateDTO dto) {
    if (!BizNoGenerator.gtZero(dto.getReportQuantity())) {
        throw new BusinessException(ErrorCode.PARAM_ERROR, "报工数量必须大于 0");
    }
    BigDecimal sum = dto.getQualifiedQuantity().add(dto.getDefectQuantity());
    if (sum.compareTo(dto.getReportQuantity()) != 0) {
        throw new BusinessException(ErrorCode.PARAM_ERROR,
            String.format("合格数(%s) + 不良数(%s) 必须等于报工数(%s)，当前合计 %s", ...));
    }
}
```

**为什么不能只靠前端**：
1. 前端校验可以被绕过（直接调接口）
2. 三者不一致会让**合格率、良品统计全部失真**
3. 质量数据是制造业的核心数据，不能有"可能是错的"空间

实测：
```
[数量不匹配] FAIL [40000]: 合格数(15) + 不良数(3) 必须等于报工数(20)，当前合计 18
```

### 1.3 防超报：条件更新（并发安全）

```sql
UPDATE work_task
SET reported_quantity = reported_quantity + #{qty},
    qualified_quantity = qualified_quantity + #{qualified},
    defect_quantity   = defect_quantity   + #{defect},
    actual_hours      = actual_hours      + #{hours},
    update_time = NOW()
WHERE id = #{taskId}
  AND status = 2                                 -- 必须 IN_PROGRESS
  AND reported_quantity + #{qty} <= plan_quantity -- 🔑 超报校验
```

判影响行数：`0` → 抛 `QUANTITY_EXCEED_PLAN(40905)`。

**如果写成"先查后改"**：

```
计划 100，已报 90
t1  工位A: SELECT reported=90 → 90+15=105 > 100? 不，A 报 10 → 100 ≤ 100 ✅
t2  工位B: SELECT reported=90 → 90+10=100 ≤ 100 ✅   ← 读到的是旧值
t3  工位A: UPDATE reported = 100
t4  工位B: UPDATE reported = 100     ← 覆盖，实际应是 110，但只记了 100
```

或者反向：

```
t1  A: SELECT 90, 准备报 20 → 90+20=110 > 100，拒绝
（但实际上报工失败的原因判断依据可能已过期）
```

**条件更新把"判断 + 更新"压进一条 SQL，从根上消除窗口期。**

实测：
```
[超报校验] FAIL [40905]: 报工数量超出计划数量：计划 100.0000，已报 40.0000，本次 70
```

### 1.4 报工幂等：单号是幂等键

```java
String reportNo = dto.getReportNo();
if (reportNo != null && !reportNo.isBlank()) {
    if (reportMapper.countByReportNo(reportNo) > 0) {
        // 已处理过 → 直接返回，不重复累加
        return buildIdempotentResult(exist);
    }
}
```

**为什么需要**：报工是**用户提交**的操作，必须防重复提交：
- 网络重试
- 用户双击
- 前端超时后重发

**没有它，"点两次提交"就会产生两条报工记录，数量翻倍。**

**并发兜底**：`uk_report_no` 唯一索引。并发重复提交时捕获 `DuplicateKeyException` → 整个事务回滚 → 累加也不会生效。

实测：
```
第一次：RP-TEST-002 报 40 → 累计 40
第二次：同一单号重复提交 → OK=True msg=报工成功 累计报工仍为=40.0000 ✅（未翻倍）
```

### 1.5 报满后的流转（质检门禁）

```java
public WorkTaskStatus afterReport(Long taskId, Long operatorId) {
    WorkTask task = getTask(taskId);
    BigDecimal reported = task.getReportedQuantity();
    BigDecimal plan = task.getPlanQuantity();
    if (reported.compareTo(plan) < 0) {
        return current;   // 没报满，保持进行中
    }
    WorkTaskStatus target = (task.getIsInspection() == 1)
            ? WorkTaskStatus.WAIT_INSPECTION    // 质检点 → 待质检
            : WorkTaskStatus.COMPLETED;         // 非质检点 → 直接完成
    workTaskMapper.finishTask(taskId, target.getCode(), current.getCode(), operatorId);
    return target;
}
```

## 2. 消息可靠性：三个丢失环节与三端加固

### 2.1 消息可能在三个环节丢失

```
生产者 → [①发送丢失] → Broker → [②Broker宕机丢失] → 消费者 → [③消费失败丢失]
```

| 环节 | 丢失原因 |
|---|---|
| ① 生产者 | 网络抖动、Broker 未收到、发送异常被吞、**事务回滚但消息已发** |
| ② Broker | 消息未持久化，Broker 重启丢失 |
| ③ 消费者 | 消费异常、进程崩溃未 ACK、消息被无限重投（毒消息） |

### 2.2 加固一：本地消息表（outbox）

**解决什么问题**：

```
❌ 直接发 MQ：
   ① 业务事务提交成功 → ② 发 MQ 前进程崩溃 → 消息永久丢失 → 工单永远不完工（业务事故）

✅ outbox：
   ① 业务写入 + outbox 记录【同一事务】提交
   ② 定时任务扫 outbox 投递
   ③ 投递成功才标记 status=1
```

**实现**：

```java
@Transactional(rollbackFor = Exception.class)
public ReportResultVO report(ReportCreateDTO dto) {
    // ... 业务写入：累加、插报工明细

    // 🔑 事务内写 outbox（不直接发 MQ）
    MqConstants.ReportCompletedEvent event = new MqConstants.ReportCompletedEvent(...);
    outboxSender.enqueue(
        "report:" + report.getId() + ":order-progress",   // 业务幂等键
        MqConstants.EXCHANGE,
        MqConstants.RK_REPORT_COMPLETED,
        event);
    return vo;
}
```

outbox 表用 `INSERT IGNORE` + 唯一索引 `uk_outbox_biz(biz_key, exchange_name)` 保证幂等：

```sql
INSERT IGNORE INTO mq_outbox
    (biz_key, exchange_name, routing_key, payload, status, retry_count, next_retry_time, create_time, update_time)
VALUES (#{bizKey}, #{exchangeName}, #{routingKey}, #{payload}, 0, 0, NOW(), NOW(), NOW())
```

**outbox 状态机**：

```
0 待投递 ──confirm ack──> 1 已投递
   │
   ├── 重试耗尽 ──> 2 投递失败（终态，告警）
   └── 路由退回 ──> 0（重置待投递）
```

### 2.3 加固二：必须等 publisher confirm

```java
CorrelationData correlation = new CorrelationData(String.valueOf(msg.getId()));
rabbitTemplate.send(msg.getExchangeName(), msg.getRoutingKey(), message, correlation);

// 🔑 必须等 confirm
CorrelationData.Confirm confirm = correlation.getFuture()
        .get(confirmTimeoutSeconds, TimeUnit.SECONDS);

if (confirm.isAck()) {
    outboxMapper.markSent(msg.getId());
} else {
    outboxMapper.markRetry(msg.getId(), "nack: " + confirm.getReason(), maxRetry);
}
```

**为什么**：`rabbitTemplate.send()` 只是把字节写进 **TCP 缓冲区**，不代表 Broker 收到了。
只有 confirm 的 ack 才能证明消息进了 Broker。

### 2.4 路由失败的隐蔽坑（最容易漏）

**问题**：消息到了交换机，但没有匹配的队列：

```
exchange 收到消息 → 找不到匹配 routingKey 的队列 → 消息被【丢弃】
但！Broker 的 confirm 依然返回 ack（它确实收到了）
```

如果不处理，outbox 会被标记"已投递"，而实际**没有任何消费者收到** → 消息静默丢失。

**解决**：开启 `mandatory=true` + 处理 returns 回调：

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated
    publisher-returns: true
    template:
      mandatory: true
```

```java
@Update("UPDATE mq_outbox SET status = 0, retry_count = retry_count + 1, "
      + "next_retry_time = DATE_ADD(NOW(), INTERVAL 30 SECOND), "
      + "last_error = #{error}, update_time = NOW() "
      + "WHERE id = #{id} AND status = 1")
int markReturned(@Param("id") Long id, @Param("error") String error);
```

### 2.5 加固三：Broker 端持久化 + 死信

```java
@Bean
public Queue reportCompletedQueue() {
    return QueueBuilder.durable(MqConstants.QUEUE_REPORT_COMPLETED)
            .withArgument("x-dead-letter-exchange", MqConstants.DLX_EXCHANGE)
            .withArgument("x-dead-letter-routing-key", MqConstants.RK_DLQ)
            .build();
}
```

| 配置 | 作用 |
|---|---|
| `durable=true` | 队列在 Broker 重启后仍存在 |
| `x-dead-letter-exchange` | 消费失败且重试耗尽的消息进死信，**不丢弃** |
| `default-requeue-rejected=false` | 🔑 防止"毒消息"无限重投把消费者线程打满 |
| `retry.max-attempts=3` + 指数退避 | 消费失败重试 3 次 |

### 2.6 重试退避（指数）

```sql
UPDATE mq_outbox
SET status = IF(retry_count + 1 >= #{maxRetry}, 2, 0),
    retry_count = retry_count + 1,
    next_retry_time = DATE_ADD(NOW(), INTERVAL LEAST(POW(2, retry_count), 300) SECOND),
    last_error = #{error}
WHERE id = #{id}
```

第 1/2/3/4/5 次重试分别间隔 2/4/8/16/32 秒（上限 300 秒），避免雪崩式重试。

## 3. 幂等：两种模式，按场景选

| 模式 | 原理 | 适用场景 | 本项目用在哪 |
|---|---|---|---|
| **A. 去重（SETNX）** | 处理前占位，占不到就跳过 | 有副作用的操作 | 库存回补、发通知 |
| **B. 重算（幂等运算）** | 结果由数据推导，算几次都一样 | 汇总类数据 | ✅ **工单进度更新** |

### 3.1 模式 B 更优，优先用

```java
// ❌ 累加：重复消费就多加一次，进度超 100%
order.setCompletedQuantity(order.getCompletedQuantity().add(qty));

// ✅ 重算：不管调几次，结果都是当前真实值
BigDecimal total = workTaskMapper.sumReportedQuantity(orderId);
order.setCompletedQuantity(total);
```

**为什么重算更好**：

| 维度 | 去重（SETNX） | 重算 |
|---|---|---|
| 依赖 | Redis（多一个故障点） | 无 |
| 键过期后 | 可能重复处理 | 无影响 |
| 消息丢失 | 数据永久错误 | **定时兜底重算可自愈** |
| 实现复杂度 | 需处理"失败释放键" | 简单 |

**完整实现**：

```java
@Transactional(rollbackFor = Exception.class)
public void recalculateProgress(Long orderId) {
    ProductionOrder order = orderMapper.selectById(orderId);
    if (order == null) return;

    int total = workTaskMapper.countByOrderId(orderId);
    int finished = workTaskMapper.countFinishedByOrderId(orderId);

    // 重算，不是累加
    BigDecimal reported  = nz(workTaskMapper.sumReportedQuantity(orderId));
    BigDecimal qualified = nz(workTaskMapper.sumQualifiedQuantity(orderId));
    BigDecimal defect    = nz(workTaskMapper.sumDefectQuantity(orderId));
    int progress = (int) Math.round(finished * 100.0 / total);

    orderMapper.recalcProgress(orderId, reported, qualified, defect, progress);

    // 完工判定也放在重算里 → MQ 丢消息时定时任务也能把工单算完工
    if (finished == total && order.getStatus() == IN_PROGRESS) {
        transit(orderId, COMPLETED, "所有工序已完成，自动完工");
    }
}
```

**实测**：
```
工单最终状态: 已完工  进度: 100%
累计报工: 300.0  合格: 295.0  不良: 5.0
✓ 所有工序完成后工单自动完工
✓ 工单进度为 100%
✓ 进度重算幂等：重复重算数字不翻倍（300.0）
```

### 3.2 模式 A 的实现（有副作用时必须用）

```java
public void handleStockRestore(RestoreEvent event) {
    String key = "idempotent:stock-restore:" + event.getOrderId();
    Boolean first = redisTemplate.opsForValue().setIfAbsent(key, "1", 24, TimeUnit.HOURS);

    if (Boolean.FALSE.equals(first)) {
        log.info("重复消息，跳过: {}", event.getOrderId());
        return;
    }

    try {
        doRestore(event);
    } catch (Exception e) {
        // 🔑 关键：失败必须释放键，否则重试被自己挡住
        redisTemplate.delete(key);
        throw e;
    }
}
```

**核心原则**：

> **幂等键只能挡住"该跳过的重复"，不能挡死"该重试的失败"。**

如果不释放：第一次消费失败 → 键还在 → 重投时被挡住 → 数据永远补不回来。

### 3.3 数据库唯一索引是更强的保证

```sql
-- 唯一索引硬拦重复，不依赖 Redis
UNIQUE KEY uk_consume_key (consume_key)
```

```java
// 事务内尝试占位：返回 0 表示已处理过
int n = consumeLogMapper.tryConsume(consumeKey, topic, msgId, result);
if (n == 0) {
    log.info("重复消息，跳过");
    return;
}
```

**关键**：必须在**业务事务内**调用。处理失败回滚时，幂等记录也一起回滚，
这样重试时不会被自己挡住。

### 3.4 幂等键设计原则

| 原则 | 说明 | 反例 |
|---|---|---|
| **粒度匹配业务** | 一条消息含多个物料，幂等键要精确到 `orderId + materialId` | 只用 messageId，部分成功重投会重复处理已成功的项 |
| **放在数据库而非只在 Redis** | Redis 会丢 key、会过期 | 资损字段必须用唯一索引 |
| **失败要释放** | 否则重试被挡死 | 忘记 delete |
| **可追溯** | 用业务单号，不要随机 UUID | 用 UUID 无法排查 |

## 4. 兜底机制（异常自愈）

### 4.1 中间态卡死恢复

跨服务操作可能卡在中间态。本项目的处理：

| 场景 | 兜底 |
|---|---|
| MQ 丢消息导致工单永远"生产中" | 定时/手动 `repairStuckOrders()`：扫"所有工序终态但工单未完工"的数据并重算 |
| outbox 投递失败 | `alertFailedOutbox()` 定时告警 + `requeue-failed` 手动补偿 |
| 预留泄漏 | 定时扫过期预留释放 |

```java
// 兜底扫描 SQL
@Select("SELECT o.* FROM production_order o "
      + "WHERE o.status = 4 AND o.is_deleted = 0 "
      + "AND NOT EXISTS (SELECT 1 FROM work_task t WHERE t.order_id = o.id "
      + "                AND t.is_deleted = 0 AND t.status NOT IN (4, 5))")
List<ProductionOrder> selectAllTasksCompletedButOrderNot();
```

### 4.2 所有失败都要可观测

```java
@Scheduled(fixedDelay = 300000, initialDelay = 60000)
public void alertFailedOutbox() {
    long failed = outboxMapper.countFailed();
    long pending = outboxMapper.countPending();
    if (failed > 0) {
        log.error("[告警] 有 {} 条消息投递失败（终态），需人工介入；待投递 {} 条", failed, pending);
        // 生产环境：接钉钉/邮件告警
    }
}
```

**"静默失败"是最危险的失败** —— 系统看起来正常，数据已经错了。

## 5. 消息可靠性测试清单

> ⚠️ **诚实声明**：本机未安装 RabbitMQ，以下测试项**未做端到端验证**。
> 已实现的能力：outbox 落库（可通过数据库直接观察）、定时投递逻辑、confirm 等待、重试退避、死信配置。

| 测试场景 | 操作 | 预期结果 | 状态 |
|---|---|---|---|
| 正常投递 | 报工 | 消息发出，工单进度更新 | ⚠️ 未端到端验证（MQ 未装） |
| **MQ 宕机** | 停 MQ，报工，启动 MQ | 报工成功（outbox 落库），MQ 恢复后自动补发 | ⚠️ 未验证（MQ 未装） |
| 进程崩溃 | 报工后 kill 服务，重启 | outbox 记录仍在，重启后投递 | ⚠️ 未验证 |
| **重复消费** | 手动投递同消息 3 次 | 工单进度只更新一次 | ✅ **逻辑已验证**：重算幂等（重复重算数字不翻倍） |
| 消费失败重试 | 让消费者抛异常 | 重试 3 次后进死信 | ⚠️ 未验证（MQ 未装） |
| 路由失败 | 配置错误 routingKey | returns 回调触发，outbox 重置 | ⚠️ 未验证 |
| 死信可见 | 检查死信队列 | 有消息，日志有告警 | ⚠️ 未验证 |

**为什么重复消费的幂等性就算"M 未装"也能验证**：
因为幂等性来自"重算"这个纯函数逻辑，与消息是否真的投递无关。
只要验证"同一订单重算多次结果一致"，就等价于验证了"重复消费不会算错"。

**未验证项的诚实表述（面试时这样说）**：
> "消息可靠性这块，outbox + confirm + 死信 + 重试退避的代码是完整的，
> 但我的开发环境没装 RabbitMQ，所以只验证了 outbox 落库和重算幂等这两条，
> 真实 MQ 的投递/重复消费/死信链路没有做端到端验证。这是我这个项目的已知缺口。"

## 6. 为什么不用 Seata（面试必答）

| 维度 | Seata AT | 本项目（本地消息表 + 补偿） |
|---|---|---|
| 一致性 | 强一致 | 最终一致（秒级） |
| 可用性 | **TC 单点，挂了全链路阻塞** | 无单点 |
| 性能 | 全局锁，吞吐下降明显 | 无全局锁 |
| 复杂度 | 引入 TC、undo_log、全局锁、回滚日志 | 本地消息表 + 定时补偿 |
| MES 适配性 | **过度设计** | ✅ 匹配 |

**关键论点**：

> MES 的生产执行是**分钟级**的业务节奏，不是秒杀。
> 允许"工单已下达但工序任务延迟 1 秒生成"，
> **不允许**"因为 TC 挂了整条产线无法下达工单"。
> **可用性优先于强一致**，这是制造业系统的正确取舍。

**按场景分级，不滥用分布式事务**：

| 场景 | 是否跨服务 | 方案 |
|---|---|---|
| 工单状态变更 + 生成工序任务 | ❌ 同一服务 | **本地事务** |
| 报工 + 更新工单进度 | ✅ 跨服务 | **本地消息表 + 最终一致** |
| 工单下达 + 物料预留 | ✅ 跨服务 | 状态机 + 补偿（预留失败 → 工单置"下达失败"） |
| 质检合格 + 工序流转 | ⚠️ 本项目跨服务 | 状态机门禁（`WAIT_INSPECTION`），非分布式事务 |

## 7. 已知限制

1. **RabbitMQ 未做端到端验证**（环境限制，见 §5）。
2. **outbox 投递未加分布式锁**：多实例部署时可能重复投递（消费端幂等可兜住，但会增加压力）。
3. **消费幂等日志表已实现但主流程未接入**：当前只用"重算"模式；
   `mq_consume_log` 表为有副作用的场景预留。
4. **死信队列未接告警**：只在日志中体现，未接钉钉/邮件。
5. **未做消息积压监控**：只统计待投递/失败数量，未接入 Prometheus 指标。
